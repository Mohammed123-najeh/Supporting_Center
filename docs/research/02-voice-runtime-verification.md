## 1. Session configuration and event model (gpt-realtime-2.1-mini over WebRTC)

### Verdict (researcher)

The OpenAI API reference documents every session field we need for POST /v1/realtime/calls with gpt-realtime-2.1-mini, along with the client and server events. The defaults that matter: server_vad with threshold 0.5, prefix 300 ms and silence 500 ms, though the session.created example shows 200 ms. idle_timeout_ms is off and takes 5000-30000, server_vad only. semantic_vad eagerness defaults to auto, which equals medium. Noise reduction and transcription are off. output_modalities is ['audio'], voice is marin in the example, speed 1.0, tool_choice auto, max_output_tokens 'inf' (integers 1-4096), truncation 'auto' (ratio 1.0), tracing null. Reasoning effort is set with reasoning.effort (minimal|low|medium|high|xhigh); its default is reportedly low but undocumented. The model and the tracing config cannot change once set. Voice cannot change after the first audio, and speed only between turns. A session lasts at most 60 minutes. Prompt caching is automatic, prefix-based and best-effort. Realtime has no prompt_cache_key, cached tokens appear in usage.input_token_details.cached_tokens, and changing instructions, tools or effort mid-call, or truncating, busts the cache. Function calls are asynchronous: execute after response.done, return function_call_output, then send response.create, with only one active response at a time. Not documented: Gulf Arabic quality, whether caching works across sessions, how reasoning tokens are reported, whether the sideband receives WebRTC-only output_audio_buffer events, and the max_output_tokens conflict (4096 in the reference vs 32,000 on the model page). Phase 0 must settle these by testing. Recommended starting point: server_vad 0.55 / 300 / 650 ms with an 8 s idle timeout, far_field noise reduction, reasoning effort low, max_output_tokens 1200, truncation retention_ratio 0.8, parallel_tool_calls false, tracing null.

### Design recommendations (researcher)

- Session JSON on POST /v1/realtime/calls (worker side): {type:'realtime', model:'gpt-realtime-2.1-mini', output_modalities:['audio'], audio:{input:{noise_reduction:{type:'far_field'}, transcription:{model:'gpt-live-transcribe', languages:['ar','en'], keywords:[<clinic name>, <doctor names>]}, turn_detection:{type:'server_vad', threshold:0.55, prefix_padding_ms:300, silence_duration_ms:650, idle_timeout_ms:8000, create_response:true, interrupt_response:true}}, output:{voice:<per-clinic, default 'marin'>, speed:1.0}}, instructions:<see caching note>, tools:[8 tools in fixed order], tool_choice:'auto', parallel_tool_calls:false, reasoning:{effort:'low'}, max_output_tokens:1200, truncation:{type:'retention_ratio', retention_ratio:0.8}, tracing:null}. Read session.created/session.updated back and log the effective config, because some defaults (silence_duration_ms 200 vs 500, noise_reduction) differ between the docs and the example.
- VAD: start with server_vad, not semantic_vad. Only server_vad supports idle_timeout_ms, which a receptionist needs (prompt the caller after 8 s of silence; after a second timeout the worker ends the call). Use silence_duration_ms 600-700 rather than 500 so Gulf Arabic speakers can pause while dictating phone numbers, Emirates IDs or dates without being cut off. In Phase 0, A/B test against semantic_vad with eagerness 'auto' and 'low' (maximum waits 4 s and 8 s), and measure false cut-ins against end-of-turn latency. Optionally switch silence_duration_ms to about 900 with session.update only while collecting a phone number, then switch back.
- Noise reduction: use 'far_field' by default, because website-widget callers mostly use laptop mics or phones held away from the face. Allow per-session 'near_field' when the widget detects a headset. Keep browser getUserMedia echoCancellation and noiseSuppression on. Set threshold 0.55-0.6 for clinic waiting-room noise. Add the documented 'wait_for_user' no-op tool so background audio does not trigger replies.
- Reasoning effort: set 'low' explicitly. OpenAI recommends it for customer-support and lookup agents, and the undocumented default is reportedly 'low' anyway. Benchmark 'minimal' in Phase 0 for time to first audio. Do not change effort mid-call, because effort is part of the cached prefix. Reserve 'medium' for the gpt-realtime-2.1 fallback clinics with complex rules.
- max_output_tokens: 1200 as a runaway guard. Assistant audio uses 20 tokens per second, so 1200 tokens is about 45-55 s of speech after transcript and reasoning tokens. Alert on any response.done with status 'incomplete' and reason 'max_output_tokens'. Do not use 4096 or inf: one runaway monologue at $20/1M audio output tokens is cheap, but it harms the call.
- Truncation: a 10-minute call is roughly 2-4k user audio tokens, 5-8k assistant audio tokens, transcripts, tool output, and about 3-5k of instructions and tools, which is well under 128k. Truncation should never trigger. Keep 'auto', or retention_ratio 0.8 with no token_limits as a cache-friendly safety net. Do not set a low post_instructions limit; it would drop booking context and bust the cache. Verify in Phase 0 that session.updated echoes truncation for 2.1-mini (Azure says 2.x ignores it).
- Prompt caching: no prompt_cache_key exists, so caching depends purely on the prefix. Put one byte-identical global prompt first (role, language policy, booking rules, tool definitions in fixed order, serialized deterministically), then the per-clinic block (name, hours, doctors, services), then per-call facts. Never change instructions or tools with session.update mid-call. Inject dynamic facts such as current time, slot results and caller-identified state as system-message items (conversation.item.create role 'system') or as function outputs, not by rewriting instructions. Verify cross-session hits by logging input_token_details.cached_tokens on the first response.done of new sessions.
- Function calling: execute a tool only after response.done (status 'completed') or response.output_item.done with item.type 'function_call'. Do not act on response.function_call_arguments.done alone, because it also fires for cancelled responses. Use call_id as the idempotency key for hold_slot, book_appointment, reschedule_appointment and cancel_appointment. After conversation.item.create(function_call_output), send response.create only if no response is active. Otherwise queue it until the next response.done, and handle the 'conversation_already_has_active_response' error (code may be null) by retrying after response.done. Keep parallel_tool_calls false so holds and bookings stay ordered.
- Caller speaks while a tool runs: the API allows async function calls, so VAD will create a new response, and the model is designed to say it is still waiting. Keep write tools fast (under 1.5 s p95). Make the prompt require a one-sentence preamble in the caller's language before find_slots or book_appointment, and forbid claiming success before the tool succeeds. If an interruption cancels the response that contained the function_call, still return a function_call_output (for example {status:'superseded'}) or delete the item, so no dangling call remains.
- Language: use the documented multilingual policy. The opening greeting follows clinic settings (Arabic or English). Switch only on a substantive utterance or an explicit request, not on names, accent or isolated words. Keep preambles and tool chatter in the current language, and ask 'English or Arabic?' when uncertain. Arabic quality of 2.1-mini is undocumented, so make Gulf Arabic and code-switching the first Phase 0 gate (marin vs cedar).
- Metering: aggregate every response.done usage, including input_tokens split into text and audio, cached_tokens_details, and output_token_details, per call and per tenant, then price it with the 2.1-mini rate card. Add input-transcription usage from conversation.item.input_audio_transcription.completed (billed separately). Store rate_limits.updated snapshots for capacity alarms at 50 concurrent sessions.
- Latency: measure end-of-user-turn to first audio as output_audio_buffer.started (WebRTC) minus input_audio_buffer.speech_stopped. Note that speech_stopped already includes silence_duration_ms of waiting. If the sideband does not receive output_audio_buffer.* events, capture them on the browser data channel (oai-events) and post them to the worker, or use response.created plus the first response.output_audio_transcript.delta as a proxy.
- Privacy and ops: set tracing:null at creation (it cannot be changed once enabled) and tracingDisabled:true in the Agents SDK. Send OpenAI-Safety-Identifier as a hashed per-call or caller ID, never a phone number. End the call at 10 minutes from the worker using a short out-of-band 'wrap up' instruction, then POST /v1/realtime/calls/{call_id}/hangup.

### Fact-check: the verdict holds

I checked the factual findings one by one against the primary sources: the calls, client-events and server-events references, the VAD, voice-prompting, voice-latency-cost, realtime-conversations, prompt-caching, your-data and realtime guides, the model pages, and the GA blog post. Almost all of them hold, including the edge cases: the 500 ms schema default against the 200 ms example, the 4096 cap against the 32,000 on the model page, idle_timeout being server_vad only, voice being locked after the first audio, and tracing being immutable once enabled.

Two claims need corrections:
- **Write-tool retry wording:** the guide says 'Do not repeatedly call the same tool with the same arguments after failure', not 'never repeat'.
- **Community regression report:** the carlos_ds report concerns 'Realtime 2.1' and 'Realtime 2', not specifically 2.1-mini.

The Location-header claim is true, but its source is the voice-server-controls guide; the calls reference does not mention it.

The factual verdict stands. The recommended starting configuration has two practical gaps, though:
1. **The SDK overwrites the call-creation config.** With @openai/agents-realtime v0.21.0, connect({callId}) immediately sends a session.update built on the SDK defaults: semantic_vad, gpt-4o-mini-transcribe and noise_reduction null. It also sends tracing:'auto' on session.created unless tracingDisabled is true. The server_vad, idle_timeout and far_field values set at POST /v1/realtime/calls are therefore silently replaced unless they are repeated in the RealtimeSession config.
2. **The recommended transcription model may not fit.** The transcription guide says gpt-live-transcribe 'doesn't support `server_vad` or `semantic_vad`' and needs manual input_audio_buffer.commit, so it probably does not belong in a VAD-driven speech-to-speech session.

**Still unverified:** the default reasoning effort (forum only), whether truncation is honored for 2.x, whether caching works across sessions, how reasoning tokens are counted, and whether the sideband receives output_audio_buffer events.

### Problems with the recommendations (fact-checker)

- The worker config is incomplete because of how the SDK behaves. In @openai/agents-realtime v0.21.0 (and on main), the websocket transport calls updateSessionConfig right after connecting with callId. _getMergedSessionConfig fills any missing fields from DEFAULT_OPENAI_REALTIME_SESSION_CONFIG: turnDetection {type:'semantic_vad'}, transcription {model:'gpt-4o-mini-transcribe'}, noiseReduction null, and pcm 24 kHz formats. So the server_vad, idle_timeout_ms, threshold, silence, far_field and transcription values set only in the POST /v1/realtime/calls session JSON are overwritten. Every audio.input setting, plus voice, tool_choice, reasoning and parallelToolCalls, must also be in the RealtimeSession/agent config. Phase 0 should log session.updated after connect. Source: https://github.com/openai/openai-agents-js/blob/v0.21.0/packages/agents-realtime/src/openaiRealtimeBase.ts
- Transcription model: the realtime-transcription guide says gpt-live-transcribe 'doesn't support `server_vad` or `semantic_vad`' and that turns end with input_audio_buffer.commit. All its examples are transcription-only sessions, and the VAD guide repeats the commit requirement. Using it, with languages[] and keywords[], inside a server_vad speech-to-speech session is unverified and probably incompatible. Start with gpt-4o-mini-transcribe or gpt-4o-transcribe (the SDK default is VAD-driven). Leave language unset for Arabic–English code-switching, or use the prompt field for clinic and doctor names. gpt-transcribe's committed-turn mode 'requires a WebSocket connection' and needs a separate test.
- Tracing: tracing:null at creation is right, but tracingDisabled:true in RealtimeSession is mandatory, not optional. Without it the SDK resolves tracing to 'auto' and sends session.update {tracing:'auto'} on session.created. Tracing cannot be modified once enabled, which conflicts with the project's 'OpenAI tracing disabled' rule.
- truncation:{type:'retention_ratio', retention_ratio:0.8} in the creation JSON: Azure documents that 2.x models don't support truncation in session.update. OpenAI's behaviour for 2.x is unverified and could fail the call creation or be ignored. A 10-minute call is far below 128k, so leave truncation out (the default is 'auto') and test it separately in Phase 0. Also note the SDK does not send truncation or max_output_tokens unless they go through providerData.
- Tool execution: the raw-event plan (execute on response.done or output_item.done, queue response.create, retry on collision) duplicates what the Agents SDK already does. v0.21.0 emits function_call on response.output_item.done or added when item.status === 'completed', then calls sendFunctionCallOutput and response.create through a ResponseCreateSequencer that waits for a free response slot. Keep the call_id idempotency inside the tool handlers, but build on the SDK's flow rather than a parallel manual one.
- max_output_tokens 1200 has an unverified basis. It is unknown whether reasoning tokens and the commentary preamble count toward it; usage shows only text and audio output tokens. A turn with a preamble, a tool call and a final answer could hit status 'incomplete' with reason max_output_tokens. Treat 1200 as a Phase 0 parameter, not a settled value.
- Wrap-up at 10 minutes: an 'out-of-band' response (conversation:'none') is not added to the conversation, and elsewhere the findings recommend text modality for out-of-band responses. For a spoken goodbye, use an in-band response.create with per-response instructions, then wait for output_audio_buffer.stopped before the hangup. The sideband may not receive that event, which is unverified, so you may need a timeout fallback.
- The caching layout (global prompt, then clinic block, then per-call facts) and 'don't change effort mid-call' come from the general prompt-caching guide, which does not mention Realtime. Cross-session reuse for Realtime is undocumented. Also note that the Agents SDK resends instructions and tools on every agent update or handoff, so tool order must stay deterministic in the agent definition.
- Noise reduction 'far_field' for 'phones held away from the face' is a guess. Mobile-browser callers holding the handset to the ear fit 'near_field' (close-talking). Make this a Phase 0 A/B test rather than a default based on that reasoning.
- Concurrency: the 50-concurrent-session target has no documented Realtime limit; the model pages list only RPM and TPM. Azure documents separate concurrent-session quotas, and OpenAI's new Live API lists concurrent-session limits per tier. Confirm with OpenAI before relying on 50.

### Facts the fact-checker added

- How the Agents SDK v0.21.0 treats the session config on connect({callId}): it sends a full session.update that falls back to SDK defaults (semantic_vad, gpt-4o-mini-transcribe, noise_reduction null) for any audio.input fields not set in RealtimeSession config. Source: openaiRealtimeWebsocket.ts and openaiRealtimeBase.ts at tag v0.21.0.
- Agents SDK tracing behaviour: unless tracingDisabled is true, it sends session.update {tracing:'auto'} after session.created. It also has historyStoreAudio (default false), which matters for the 'no audio stored' rule.
- Agents SDK v0.21.0 includes a ResponseCreateSequencer that serialises response.create, and it auto-executes tools on response.output_item.done with status 'completed'.
- OpenAI now also offers a separate Live API (POST /v1/live/sessions, WebRTC and WebSocket) with model gpt-live-1. It costs $0.05 per minute billed per second (backend model and tool usage billed separately) and has concurrent-session rate limits: Build 50, Launch 300, Grow 500. It is not available on /v1/realtime. This is relevant to the concurrency target and to model choice. Source: https://developers.openai.com/api/docs/models/gpt-live-1.md
- Azure's 2.1 page gives a 256,000-token context window, but OpenAI's model pages give 128,000 for both gpt-realtime-2.1 and 2.1-mini.
- gpt-realtime-2.1 fallback pricing per 1M tokens: text $4 input, $0.40 cached, $24 output; audio $32 input, $0.40 cached, $64 output. Its rate limits are the same as 2.1-mini. Source: https://developers.openai.com/api/docs/models/gpt-realtime-2.1.md
- The 2.1 announcement (Jul 6 2026) says p95 latency fell by at least 25% across Realtime voice models through improved caching, and that 2.1 improved alphanumeric recognition, silence and noise handling, and interruptions. It says nothing about Arabic. A forum post says gpt-realtime-mini is scheduled for deprecation (secondary).
- gpt-live-transcribe needs turn_detection null and a manual commit, and gpt-transcribe's committed-turn workflow requires a WebSocket. Source: https://developers.openai.com/api/docs/guides/realtime-transcription.md
- error.code is optional, and the reference gives no list of codes. The only documented example is 'invalid_event'. 'invalid_request_error' and 'server_error' are error types, not codes.
- The general prompt-caching guide gives in-memory retention of about 5-10 minutes of inactivity (up to 1 hour) for pre-GPT-5.6 models and says ZDR orgs default to in_memory. It does not cover Realtime.
- A community report says sideband connections return 404 call_id_not_found when the call was created with an ephemeral key. This is consistent with the project's choice of a standard key (secondary): https://community.openai.com/t/ephemeral-keys-trigger-realtime-sideband-404-errors/1396002
- The voice-prompting guide says 'English is the default response language' and suggests asking 'Would you like me to continue in English or [LANGUAGE]?' when confidence is low.

### Open questions

- max_output_tokens: the reference allows integers 1-4096 or 'inf', but the gpt-realtime-2.1-mini model page says 32,000 max output tokens. Do reasoning tokens count toward max_output_tokens, and where are they billed? usage.output_token_details has only text_tokens and audio_tokens.
- The default reasoning.effort for gpt-realtime-2.1-mini is only confirmed by a forum reply ('low'). The voice-prompting migration step ('Set reasoning effort to `low` instead of the default') implies the default is not low. Check this in Phase 0 by reading session.created.
- Prompt caching across separate Realtime sessions: is a byte-identical instructions-plus-tools prefix reused across calls in the same org? What are the minimum cacheable prefix length and TTL for realtime models, and does ZDR force in-memory-only caching for /v1/realtime? None of this is documented.
- Does the server sideband WebSocket (?call_id=) receive the WebRTC-only events (output_audio_buffer.started/stopped/cleared) and response.output_audio.delta, or do these go only on the browser data channel? This determines where latency metrics are captured.
- The default silence_duration_ms is 500 ms in the reference but 200 ms in the session.created example (gpt-realtime-2025-08-28). What is the actual default for 2.1-mini? Is noise_reduction null by default for 2.1-mini?
- Gulf Arabic (and Arabic–English code-switching) quality, dialect fidelity and voice suitability (marin vs cedar) for gpt-realtime-2.1-mini: OpenAI has published nothing; Phase 0 must test it.
- Does OpenAI (not Azure) honor 'truncation' (retention_ratio/token_limits) for the 2.x realtime models? Microsoft Foundry says 2.x ignores it.
- The full list of Realtime error codes is not documented. 'conversation_already_has_active_response' is known only from the community and GitHub, and its code is sometimes null.
- Input transcription over WebRTC: the realtime-transcription guide says committed-turn gpt-transcribe 'requires a WebSocket connection'. Is it usable on a WebRTC call with a sideband, or must we use gpt-live-transcribe? The reference also says 'delay' is supported only with gpt-realtime-whisper, while the guide uses it with gpt-live-transcribe.
- The 16,384-token limit on instructions plus tools was documented for gpt-realtime. Is the limit the same for gpt-realtime-2.1-mini?
- Does changing turn_detection mid-call (e.g. a longer silence while capturing phone numbers) affect the cached prefix or trigger any session reset? Not documented.
- Concurrent-session limits for Realtime are not documented. Model pages list only RPM/TPM per tier, so the 50-concurrent-session target needs confirmation from OpenAI sales or support.
- The response 'phase' field (commentary/final_answer) appears in the prompting guide but not in the reference schema. Is it reliably present on 2.1-mini, and do preamble ('commentary') audio tokens bill like normal output?
- Community reports say 2.1-mini stopped calling tools in a SIP flow and showed instruction leakage. Do these reproduce over WebRTC with our 8 tools? This needs a Phase 0 tool-calling eval.

## 2. Call lifecycle: creation, sideband, ending, errors

### Verdict (researcher)

The design we chose is supported and has an official reference implementation (openai-agents-js examples/realtime-server-controlled). The server POSTs multipart sdp and session to /v1/realtime/calls with a standard key and an OpenAI-Safety-Identifier. It gets 201 with the SDP answer and a relative Location /v1/realtime/calls/rtc_…, then attaches the Agents SDK RealtimeSession over wss://api.openai.com/v1/realtime?call_id=… (Bearer auth). It returns the answer only after session.updated confirms our instructions and tools. Hangup (POST /v1/realtime/calls/{id}/hangup) works for WebRTC; it returns 200 when termination begins and 404 when the call is unknown. Accept, reject and refer are SIP-only. An audio-only offer with no data channel is the officially recommended way to keep control on the server, but only if the SDP policy is enforced on the server for both the offer and the answer. The trade-off is that we lose WARP's pre-negotiated data channel and must give the widget its own app channel. Errors: the in-session `error` event is usually recoverable. Call creation should retry only on 429 slow_down and 503 server_is_overloaded, honouring Retry-After plus jitter within a tight attempt and time budget, and never on quota or billing errors. Important gaps are undocumented: sideband re-attach, multiple sidebands, keepalive, what the browser sees after hangup, behaviour at the 60-minute limit, and the lifetime of a created call that never connects. Design for 'any failure leads to idempotent hangup' and verify these points in Phase 0. On residency, /v1/realtime (including gpt-realtime-2.1-mini) is listed for US and EU processing but not for the UAE region. Whether the calls endpoint, the sideband and the WebRTC media plane are regional under eu.api.openai.com is unconfirmed, and the SDK hardcodes api.openai.com for callId, so an EU deployment needs explicit URL overrides. Realtime tracing must be disabled because it cannot be turned off once enabled and is not EU-residency compliant.

### Design recommendations (researcher)

- CALL STATE MACHINE (voice worker; one record per call keyed by a browser-generated app_session_id UUID, persisted in Postgres/Redis — not memory only, unlike the example). States: RESERVED → CREATING_CALL → ATTACHING_SIDEBAND → ANSWER_SENT → MEDIA_CONNECTED/ACTIVE → WRAPPING_UP → HANGING_UP → CLOSED, plus FAILED_SETUP and ORPHAN_CLEANUP. Every terminal path goes through one idempotent cleanup: close the RealtimeSession, POST /hangup (treat 404 as success), flush the transcript and outcome. This mirrors the example's 'all converge on idempotent cleanup'.
- RESERVED: check clinic auth and origin, Origin/CSRF on the iframe endpoint, the per-clinic concurrency cap, the global cap of 50 live calls, and one call per browser session. Reject an app_session_id that was already cancelled or used, so a replayed SDP POST cannot create a second call. Run the SDP policy here, before any OpenAI call: Content-Type application/sdp, ≤256 KiB, starts with v=0, exactly one m=audio with a nonzero port, and no m=application or m=video. On violation return 4xx without calling OpenAI.
- CREATING_CALL: POST https://api.openai.com/v1/realtime/calls as multipart with sdp (application/sdp) and session (application/json): {type:'realtime', model:'gpt-realtime-2.1-mini', audio:{output:{voice}}, tracing:null}. Add headers Authorization: Bearer <standard key> and OpenAI-Safety-Identifier: HMAC(clinic_id + browser session), with redirect:'error' and a per-attempt timeout of about 8–10 s. On 201, parse Location strictly (rtc_ regex plus expected origin) and validate that the answer is also audio-only; if that fails, hang up the new call ID at once. Retry only on 429 slow_down, 503 server_is_overloaded, or a network error before any response. Honour Retry-After as a minimum plus jitter, at most 2 attempts within a total budget of about 6 s, because a caller is waiting. Never retry 400/401/403/404, credit or spend/usage-limit 429s, or a timeout that occurred after the request body was sent: no idempotency key is documented, so a blind retry can leave an orphan call we cannot hang up. On 503 overload, optionally retry once with the clinic's fallback model (gpt-realtime-2.1) if the clinic allows it. On final failure return a friendly 'busy' state and offer request_callback through a non-voice form.
- ATTACHING_SIDEBAND: new RealtimeSession(agent, { transport:'websocket', model: <same model as create>, tracingDisabled:true, context:{clinicId, callId, appSessionId} }). Register listeners for transport_event, error and transport 'disconnected' before calling connect({ apiKey, callId }). Wait for a session.updated that contains our instructions and all 8 tool names, with a timeout of 10 s (from the example). Retry the attach once after about 500 ms on a 404 call_id_not_found or a socket error, then fail. On failure, hang up and return 503 to the browser. Return the SDP answer only after the session is ready, so the caller never hears a model running on default instructions without tools.
- ANSWER_SENT → MEDIA_CONNECTED: no server event is documented for 'ICE connected'. Have the widget report pc.connectionState === 'connected' over our own signaling channel (SSE or WS, carrying app events only), with a timeout of 15 s; if it expires, hang up. Trigger the greeting (response.create from the sideband) only after media is connected, so the opening is not spoken into a dead link. A Phase 0 test should check whether audio sent before ICE completes is lost.
- ACTIVE: start a hard 10-minute timer from MEDIA_CONNECTED. At about 9:00 send a wrap-up instruction (session.update or a system item) so the agent offers to finish or book a callback. At 10:00 enter WRAPPING_UP. Use server_vad with idle_timeout_ms of about 8000–10000 to re-prompt a silent caller, and keep an app-level counter: after 2 consecutive timeout_triggered events with no speech, say goodbye and enter WRAPPING_UP. Drive the speaking/listening UI from output_audio_buffer.* and input_audio_buffer.speech_*, not from response.done. Log every `error` event with our client event_id. Count response.done with status failed or incomplete; after 3 in a row, apologise, offer request_callback, and wrap up. Tool failures must return a structured error to the model rather than throw. Authorize every tool against runContext.context (clinic and call), never against tool arguments. Track rate_limits.updated and alert when remaining tokens fall below about 20%.
- WRAPPING_UP → HANGING_UP: stop accepting new tool calls. Let a booking already in progress finish (with an idempotency key per hold or booking), then wait for output_audio_buffer.stopped of the goodbye, capped at about 8 s. Notify the widget over our app channel (call_ended plus reason) before calling hangup, because what the browser observes after a server hangup is undocumented. POST /hangup with the SDK's own retries disabled; on failure, put the call ID in a durable cleanup queue retried every 30–60 s with backoff. Hangup only begins termination (200 = 'begins terminating'), so wait for the sideband to close, up to about 5 s, then force-close it locally.
- FAILURE TRANSITIONS: (a) Sideband 'disconnected' during ACTIVE: try one re-attach with the same call_id within about 2–3 s. This is undocumented; the official example does not re-attach, so validate it in Phase 0. If it fails, hang up and send call_dropped to the widget with a callback offer. (b) Widget reports pc 'failed', or 'disconnected' for more than 10 s, or the app channel heartbeat is lost for more than 15 s: hang up, because the sideband may not be told the browser left (issue #684). (c) Worker SIGTERM: stop accepting; give active calls up to about 30 s to wrap up, then hang up everything; the next worker's sweeper hangs up any call IDs left in the durable table. (d) Sweeper: every 60 s, hang up any call older than 11 minutes, or stuck in a setup state for more than 60 s, as a safety net under the 60-minute provider maximum.
- SECURITY: no data channel and the SDP policy enforced on both offer and answer, so the browser cannot send session.update or response.create or read transcripts. Keep the call_id, instructions, tools and raw errors server-side. Expose only allowlisted app events to the iframe. Use a standard API key on the server only, never ephemeral keys (this also avoids the reported ephemeral-key sideband 404s). Set the Safety-Identifier on call creation, and consider adding it to the sideband handshake through the SDK's createWebSocket() hook until it is confirmed unnecessary. Set tracing:null in the create body and tracingDisabled:true in the SDK, because tracing cannot be turned off once on and is not EU-residency compliant.
- RESIDENCY: the UAE region (ae.api.openai.com) does not list /v1/realtime, so UAE-resident Realtime is not available today. If EU residency is chosen, you must change all three hostnames: (1) POST to https://eu.api.openai.com/v1/realtime/calls, (2) connect({ url: 'wss://eu.api.openai.com/v1/realtime?call_id=' + callId, apiKey }), because the SDK hardcodes api.openai.com for callId, and (3) set the OpenAI client baseURL for hangup and change the Location-origin check copied from the example. Confirm with OpenAI that /v1/realtime/calls, the sideband and the WebRTC media plane are all in-region. Media IPs in the answer SDP are not documented as regional.
- CAPACITY: 50 concurrent calls is likely to exceed the Build tier's 200,000 TPM for gpt-realtime-2.1-mini once contexts grow. This is my own estimate, not from a source. Plan for the Launch tier (4,000,000 TPM), and ramp traffic gradually to avoid 429 slow_down. Keep a worker-side semaphore so we fail fast locally rather than hitting OpenAI limits mid-call.
- PHASE 0 TESTS to add: re-attach after a sideband drop, and whether the call survives; two sidebands on one call; what the browser PC sees after server hangup (connectionState, track 'ended'); whether the sideband is notified when the browser closes its PC; the lifetime of a created call whose answer is never applied; latency of call creation plus attach plus session.updated (budget about 1.5 s at p95); how much DTLS 1.3 helps without WARP.

### Fact-check: the verdict holds

The findings are accurate overall. I re-checked them against the OpenAPI spec, the developers.openai.com guides, the realtime-server-controlled example and the SDK at tag v0.21.0. npm latest for @openai/agents is 0.21.0. Every substantive technical claim holds: the multipart create with the 201 + Location response; hangup working for WebRTC and SIP; accept/reject/refer being SIP-only; the sideband via ?call_id with Bearer auth; the SDK hardcoding api.openai.com for callId; tracing defaulting to 'auto' and being impossible to change once on; the residency table with no UAE Realtime; and the retry guidance. The corrections are minor. (1) The sample call ID rtc_u1_9c65… was not found; the spec's sample is rtc_u0_479a275623b54bdb9b6fbae2f7cbd408. (2) Accept and reject also document 409 and 500, not only refer. (3) The 256 KiB and v=0 rules come from sdpPolicy.ts, not the README. (4) The OpenAI_Support SIP reply was tentative ('Seems like… resolved'). (5) That the sideband receives output_audio_buffer.* is implied by the example, not documented. Two items partly answer the open questions. First, Realtime billing is per Response (tokens) with no connection cost, so a call that never connects should not be billed unless a response is created. Second, secondary forum evidence suggests that closing the sideband does not end the call, and that re-attach works while the call is live, returning 404 once it has ended. The verdict holds: the design is supported and has an official reference implementation; any failure should lead to an idempotent hangup; and re-attach, multiple sidebands, keepalive, behaviour at the 60-minute limit and in-region media must be verified in Phase 0 or with OpenAI.

### Problems with the recommendations (fact-checker)

- CREATING_CALL safety identifier HMAC(clinic_id + browser session): the docs say to use a 'stable, privacy-preserving value, such as a hashed internal user ID' so OpenAI can target enforcement at an individual user. A per-browser-session value is not stable. Prefer a stable pseudonymous ID (for example an HMAC of a long-lived first-party widget cookie or device ID scoped per clinic), and check it with the privacy/legal track.
- Copying from the example: the example itself leaves tracing on (SDK default 'auto'). The recommendation to set tracing:null and tracingDisabled:true is correct and must be treated as mandatory, not optional, because otherwise the first sideband session.update enables tracing permanently. The same applies to any re-attach.
- ATTACHING_SIDEBAND retry: the reported 404 call_id_not_found arrived about 5.5 s after the handshake began, so 'retry once after ~500 ms' within a 10 s readiness timeout may not fit. Set an explicit total attach budget. Each retry needs a new RealtimeSession, because connect() throws if the transport is not 'disconnected'. Use the same standard key for create and attach (forum same-key finding).
- FAILURE (a) re-attach: secondary forum evidence supports it (re-attach works while the call is live and returns 404 after it ends), but it is still undocumented. A re-attached SDK session resends instructions and tools, while the server-side conversation keeps going, so local transcript and pending tool-call state must come from our durable store. Keep it as a Phase 0 test, as the design says.
- ACTIVE idle re-prompt with server_vad: idle_timeout_ms is server_vad-only and measured from response.done plus playback. If Block 2 chooses semantic_vad for Arabic, this mechanism is unavailable and an app-level silence timer is needed instead.
- Keepalive is not addressed in the state machine. The SDK sends no pings. Decide whether to add ws-level pings with a tolerant timeout, or rely on TCP, and test sideband behaviour during long silences in Phase 0.
- ANSWER_SENT greeting: delaying response.create until the widget reports 'connected' is also cost-safe. Realtime bills only when a Response is created, so creating a call that never connects costs nothing unless a response is triggered. This supports the design; it does not conflict with it.
- RESIDENCY: the design is consistent with the docs (no UAE /v1/realtime; EU needs eu.api.openai.com overrides for create, the sideband url and the hangup baseURL). The docs never name /v1/realtime/calls or the WebRTC media plane, so EU residency for media is unverified and must be confirmed in writing with OpenAI before relying on it.

### Facts the fact-checker added

- The official example does NOT disable tracing. server.ts sessionOptions has no tracingDisabled and realtimeCall.ts sends no tracing:null, so the SDK's first sideband session.update sends tracing 'auto', and that cannot be undone. Copying the example as is would break the 'tracing disabled' and EU-residency requirements. Set both tracing:null in the create body and tracingDisabled:true.
- Example README: 'Cleanup state is in memory only; this example does not guarantee cleanup after process termination.' This directly supports the durable call table in the design.
- SDK v0.21.0 openaiRealtimeWebsocket.ts has no ping/pong or keepalive code. ## 3. Caller transcription and Arabic/English handling

### Verdict (researcher)

There is no clean, documented, non-deprecated transcription model for a WebRTC voice-agent session that uses VAD. gpt-live-transcribe ($0.017/min) and gpt-realtime-whisper ($0.017/min) both require turn_detection null, so they conflict with our semantic_vad/server_vad session. The two that do support v1/realtime, gpt-4o-transcribe ($0.006/min) and gpt-4o-mini-transcribe ($0.003/min), are deprecated and shut down on 26 Feb 2027. The Agents SDK 0.21.0 also defaults silently to gpt-4o-mini-transcribe. The best candidate is gpt-transcribe ($0.0045/min, languages ['ar','en'], keywords for doctor and clinic names, a short context prompt). OpenAI's guide says it works for input transcription in Realtime sessions, but also that it 'requires a WebSocket connection', and its model page omits v1/realtime. So Phase 0 must first prove it is accepted in our /v1/realtime/calls WebRTC sessions configured over the sideband. Otherwise the fallbacks are gpt-4o-transcribe until February 2027, then out-of-band transcription by gpt-realtime-2.1-mini. Caller transcripts are an approximate record only, so booking data must come from validated tool arguments with digit-by-digit read-back. OpenAI publishes a solid multilingual prompting pattern: default language, switch only on a substantive utterance, ignore accent and names, ask when unsure. It has no Arabic-specific guidance, no Arabic voice recommendation beyond 'marin or cedar for best quality', and no official Arabic evaluation. The third-party evidence is thin: GPT-4o-transcribe at about 36% WER on Gulf speech, and GPT-Transcribe at about 19% on a small Saudi call-centre sample. Phase 0 therefore has to measure Emirati/Gulf CER/WER, code-switched script behaviour, entity accuracy, silence hallucinations, transcript latency and output-language drift on our own audio.

### Design recommendations (researcher)

- Treat the caller transcript as a record for logs, staff review and the 30-day store, never as booking data. OpenAI's own docs say it "may diverge" from what the model heard. Take names, dates and phone numbers only from tool-call arguments, validate them server-side, and have the model read identifiers back digit by digit.
- Preferred transcription config, pending Phase 0: audio.input.transcription = { model: 'gpt-transcribe', languages: ['ar','en'], keywords: [per-clinic doctor names in Arabic and Latin script, clinic name, branch/area names, specialties], prompt: <one or two sentences, e.g. 'Call to a UAE clinic receptionist. Callers speak Gulf (Emirati) Arabic and English, often mixed in one sentence. Transcribe verbatim in the script spoken; do not translate.'> }. It is the cheapest non-deprecated model at $0.0045/min, returns detected `languages`, uses earlier turns as context, and was the best Saudi call-centre performer in the one public comparison. Do not send `language` and `languages` together.
- Always set the transcription model explicitly in the RealtimeSession config. The Agents SDK 0.21.0 default is gpt-4o-mini-transcribe, which shuts down on 26 Feb 2027.
- Do not configure gpt-live-transcribe or gpt-realtime-whisper inside the voice-agent session. Both require turn_detection null, and we rely on semantic_vad/server_vad to trigger replies.
- Fallback ladder if Phase 0 shows gpt-transcribe is rejected or silent in a WebRTC call: (a) gpt-4o-transcribe (not mini) with a free-text prompt, as a temporary measure only, ending 26 Feb 2027 with a migration ticket opened now; (b) out-of-band transcription by gpt-realtime-2.1-mini, sending a text-only response.create with conversation 'none' and only the latest user item after each input_audio_buffer.committed (cookbook estimate 3-5x ASR cost); (c) store only assistant transcripts plus tool calls, with no caller transcript, if neither works.
- Keyword and prompt hygiene: build keywords per tenant, strip <, > and line breaks (one bad keyword rejects the whole session.update), keep the list short and limited to names that actually occur, and keep glossaries out of the free-text prompt because of reported glossary hallucinations on near-silent segments. Discard or flag completed transcripts from very short items and those consisting only of keyword words.
- Language policy in the system prompt, adapted from OpenAI's gpt-realtime-2 multilingual block: greet in Gulf Arabic with a brief English offer (or use a per-clinic default); switch only on a substantive utterance or explicit request; never switch on accent, names, greetings, or English medical/brand terms inside Arabic sentences; keep preambles, tool bridges and confirmations in the current language; if unsure, ask once in both languages. Write the Arabic instructions and sample phrases in Gulf dialect, not MSA, and tell the model to avoid MSA formality.
- Number and date handling: tell the model to convert spoken Arabic or English numbers to Western digits in tool arguments, read UAE mobile numbers back digit by digit in the caller's language, read dates and times plainly ('Tuesday the 4th at 3:30 pm' / Gulf Arabic equivalent), and confirm before book/reschedule/cancel.
- Unclear-audio rules from the guide: respond only to clear audio, don't guess, don't repeat the same clarification twice, and skip reasoning on unclear audio. Use reasoning effort 'low' and short one-sentence preambles before slow tools.
- Voices: shortlist marin and cedar (OpenAI's quality recommendation) and have native Emirati listeners A/B them on Arabic and code-switched output. The voice is fixed per session, so choose it per clinic at session creation. Keep speed at 1.0 and adjust pacing through instructions, because speed only changes playback rate (range 0.25-1.5, changeable between turns).
- Set audio.input.noise_reduction per measured result (start with near_field for phone browsers; compare far_field and null on laptop audio) and keep semantic_vad with eagerness tuned in Phase 0.
- Cost and audit logging: record conversation.item.input_audio_transcription.completed.usage (tokens or duration seconds) per item next to response.done usage for per-call cost. Don't enable transcription logprobs unless used. Alert on conversation.item.input_audio_transcription.failed.
- Phase 0 measurement list: (1) a config acceptance matrix of gpt-transcribe / gpt-live-transcribe / gpt-4o-transcribe × WebRTC call created via /v1/realtime/calls with session.update over the sideband × semantic_vad and server_vad, checking accepted or error text, whether completed events reach the sideband, and whether the `languages` field and "ar" code are accepted; (2) ASR accuracy on about 60-100 scripted plus free Emirati/Gulf Arabic, English and code-switched utterances in quiet, car/street and speaker-phone conditions, reporting CER (primary for Arabic) and WER after normalisation (diacritics, alef/ya/ta-marbuta, digits), plus exact-match entity accuracy for doctor names, dates, times and 05X phone numbers with and without keywords; (3) the script used for English words inside Arabic, and any translation; (4) hallucination rate on silence, noise, coughs and very short clips, including keyword-insertion false positives and empty transcripts; (5) latency from input_audio_buffer.speech_stopped to transcription completed, and to the first response audio; (6) model output quality rated by native speakers: wrong-language or MSA-instead-of-Gulf turns, drift after names, number read-back errors, voice naturalness for marin and cedar; (7) agreement between transcript and tool arguments; (8) transcription seconds billed versus wall-clock call length, to settle the billing basis.

### Fact-check: the verdict holds

I checked all 36 claims against primary sources. 26 are confirmed, 9 needed correcting, and 1 is unverifiable. The pricing, deprecation dates (26 Feb 2027), SDK 0.21.0 defaults (gpt-4o-mini-transcribe plus semantic_vad, checked at the git tag and on npm), API field names and VAD/speed defaults are all accurate. The main recommendation still holds: make gpt-transcribe the preferred caller-transcription model pending Phase 0, always set the transcription model explicitly, treat transcripts as approximate, and take booking data only from validated tool arguments.

Two parts of the reasoning need fixing.
1. The exclusion of gpt-live-transcribe is not supported. The turn_detection-null restriction is documented, and staff-confirmed, only for TRANSCRIPTION sessions; both forum threads use type 'transcription'. OpenAI's own Agents SDK v0.21.0 example puts gpt-live-transcribe in a speech-to-speech RealtimeSession with the default semantic_vad. Treat this as unverified, not as a conflict.
2. The case for gpt-transcribe is stronger than presented. OpenAI's current cost guide (voice-latency-cost) says to use gpt-transcribe for committed-turn input transcription in Realtime sessions, billed by duration. That page also partly settles the billing-basis question (per committed turn) and shows text output tokens on audio replies.

Smaller corrections:
- 'ar' is not the only candidate code. Gulf Arabic has ISO 639-3 'afb', and the newer models accept selected ISO 639-3 codes.
- The name-triggered language drift was NOT reliably fixed by a prompt instruction.
- I could not confirm that the code-switching benchmark (2605.19069) included gpt-4o-transcribe.
- The recommended transcription prompt restates the task, which OpenAI's guide advises against.

Phase 0's acceptance matrix remains the right first step. It should cover gpt-transcribe, gpt-live-transcribe and gpt-4o-transcribe, the language codes 'ar', 'ara', 'afb' and no languages field, and semantic_vad versus server_vad, all over a /v1/realtime/calls WebRTC session configured over the sideband.

### Problems with the recommendations (fact-checker)

- Recommendation 4 ('Do not configure gpt-live-transcribe or gpt-realtime-whisper inside the voice-agent session; both require turn_detection null') rests on an unverified extension of a transcription-session rule, and OpenAI's own Agents SDK example contradicts it for gpt-live-transcribe. It also conflicts with the Phase 0 matrix, which already tests gpt-live-transcribe. Downgrade it to: test gpt-live-transcribe with semantic_vad and server_vad in Phase 0, and treat it as a streaming-delta candidate if it is accepted (at about 3.8x the cost of gpt-transcribe).
- Recommendation 2's sample prompt ('Transcribe verbatim in the script spoken; do not translate.') goes against OpenAI's transcription guidance "don't restate the transcription task". Keep the prompt to context only (UAE clinic, Gulf Arabic/English code-switching, appointment booking), and test separately whether adding script or no-translation instructions helps or hurts.
- Recommendation 2's languages: ['ar','en'] assumes 'ar' is accepted, which is unverified. The Phase 0 matrix should also test 'ara' and 'afb' (ISO 639-3 Gulf Arabic) and the omission of `languages` altogether, and compare accuracy across them, not just whether each is accepted.
- The verdict's 'no clean documented non-deprecated option' overstates the gap. The cost guide documents gpt-transcribe for committed-turn input transcription in Realtime speech-to-speech sessions, and the SDK docs document gpt-live-transcribe in a RealtimeSession. What is undocumented is WebRTC plus sideband specifically, plus the conflicting WebSocket caveat in the transcription guide.
- Fallback (b)'s cost estimate (3-5x) comes from an archived recipe that used gpt-realtime and gpt-4o-transcribe prices. Recalculate it at gpt-realtime-2.1-mini text-output and cached-input rates before relying on it.
- Recommendation 11 mentions transcription logprobs. That include option was not checked in this review, so confirm the exact field name (include: item.input_audio_transcription.logprobs) before writing it into the spec.
- Voice shortlist: marin and cedar are a general quality recommendation, not an Arabic-specific one. With no Arabic validation from OpenAI, the A/B test should cover more than two voices, and the dialect/accent steerability risk (accent instructions reported ignored on gpt-realtime-2) belongs in Phase 0's go/no-go criteria.

### Facts the fact-checker added

- OpenAI's current cost guide (https://developers.openai.com/api/docs/guides/voice-latency-cost) recommends gpt-transcribe for committed-turn input transcription in Realtime (speech-to-speech) sessions. It says this is billed separately at the ASR rate and by audio duration, and gives no WebSocket-only caveat. This is the strongest primary support for the preferred option and should be cited in the verdict.
- The official Agents SDK v0.21.0 docs and example configure gpt-live-transcribe (delay 'low', prompt, keywords, languages) inside a RealtimeSession on gpt-realtime-2.1, with the SDK's default semantic_vad merged in (https://raw.githubusercontent.com/openai/openai-agents-js/v0.21.0/examples/docs/voice-agents/configureSession.ts). The SDK guide says "Use `gpt-live-transcribe` for low-latency streaming transcription". So gpt-live-transcribe may well work with VAD in voice-agent sessions. The turn_detection-null rule has only been shown for transcription sessions.
- The model-page endpoint tables are unreliable for this question. gpt-4o-transcribe and gpt-4o-mini-transcribe mark v1/realtime/transcription_sessions 'Not supported', yet OpenAI staff recommend gpt-4o-transcribe with server_vad in transcription sessions. 'v1/realtime: Not supported' on the gpt-transcribe and gpt-live-transcribe pages therefore does not rule them out as input-transcription models.
- The transcription guide says to use prompt and keywords "only for context relevant to the audio; don't restate the transcription task" (https://developers.openai.com/api/docs/guides/transcription).
- ISO 639-3 has 'afb' (Gulf Arabic) and 'ara' (Arabic macrolanguage) (https://iso639-3.sil.org/code/afb). Because the newer models accept "Selected ISO 639-3 codes", these are candidate codes alongside 'ar'.
- Audio token rates: user audio is 1 token per 100 ms and assistant audio is 1 token per 50 ms. Per the cost guide, "VAD will effectively filter out empty input audio, so empty audio doesn't count as input tokens". At 2.1-mini rates, fresh caller audio costs about $0.006/min, so gpt-live-transcribe at $0.017/min would be the largest per-minute input line item. gpt-transcribe ($0.0045) would not.
- The Agents SDK merges each field separately: an undefined `transcription` falls back to gpt-4o-mini-transcribe, and `transcription: null` turns it off. The default config also sets no voice, so the voice must be set explicitly.
- The out-of-band cookbook's cost multipliers were measured with gpt-realtime against gpt-4o-transcribe prices, not with gpt-realtime-2.1-mini. They need recalculating at 2.1-mini rates.
- Deprecations also retire gpt-realtime and gpt-realtime-mini on 20 Jan 2027, and the changelog describes GPT Transcribe as being for "final transcripts of committed Realtime turns".

## 4. Browser and network side of the widget (UAE)

### Verdict (researcher)

The iframe and WebRTC design will work, with known limits. Microphone access from the cross-origin iframe needs allow="microphone" with no origin list: WebKit ignores origin lists and breaks, and Firefox and Safari do not support wildcards. The clinic page must also not block the microphone in its own Permissions-Policy header. Chrome asks about, and stores the grant for, the clinic's top-level site (Chromium source: microphone is 'delegated', TOP_ORIGIN_ONLY_SCOPE). Firefox shows both origins. WebKit passes the top-level origin to its permission delegate; what Safari's own prompt shows is unverified. So callers will see a separate prompt on every clinic site, and a popup on our own domain is a useful fallback.

For audio, use echoCancellation, noiseSuppression and autoGainControl set to true (no exact constraints) and play remote audio through an HTMLAudioElement so Chrome's echo canceller can use it. Combine this with OpenAI's far_field noise reduction and tuned VAD. Phase 0 must still measure speakerphone self-interruption.

iOS Safari is the riskiest platform. It needs a tap to start, and capture can be lost after interruptions; recover by checking track mute and ended events, re-running getUserMedia and calling replaceTrack. Use navigator.audioSession for Bluetooth routing. A 2026 bug made getUserMedia fail after an iOS audio-daemon reset; the fix is committed, but the iOS release that ships it is unknown.

On the network side, OpenAI terminates WebRTC on geo-distributed relays and supplies no STUN or TURN. A 2025 analysis showed a TCP/443 candidate, but nothing confirms it is still offered after 2026. Neither the Agents SDK nor any OpenAI documentation offers ICE restart for an existing call, so plan for 'end and reconnect with state' and log candidate types.

For latency, combine client getStats data (candidate-pair RTT, jitter buffer, loss) and local audio-onset timing with sideband event timestamps, keyed by call_id.

In the UAE, TDRA treats real-time voice over IP as a regulated telecom service and requires licensees to block unlicensed VoIP. No source confirms whether WebRTC to OpenAI works on e& or du, and one academic study found only minor WebRTC interference. Two things need deciding before launch: test on UAE networks in Phase 0, and ask the lawyer whether an AI receptionist counts as a VoIP service under TDRA rules.

### Design recommendations (researcher)

- EMBED SNIPPET: give clinics exactly <iframe src="https://widget.<ourdomain>/c/<clinicId>" allow="microphone; autoplay" title="…">. Do not use origin lists, because Safari ignores them and breaks (WebKit 189901). Do not use '*' wildcards, because Firefox always prompts and Safari and Firefox do not support them. Do not add a sandbox attribute; if a CMS forces one, it must include allow-scripts and allow-same-origin. A small loader script that injects the iframe guarantees the correct allow attribute.
- ONBOARDING CHECK: when a clinic is onboarded, and periodically after that, fetch the clinic page and inspect its Permissions-Policy and CSP frame-src headers. If microphone=() or microphone=(self) is present, the clinic must change it to microphone=(self "https://widget.<ourdomain>"). Otherwise the iframe gets NotAllowedError with no prompt.
- POPUP FALLBACK: when the iframe cannot get the microphone (policy-blocked NotAllowedError, repeated iOS prompts, Firefox problems), offer an 'Open call in a new window' button. ### Problems with the recommendations (fact-checker)

- EMBED SNIPPET: allow="microphone; autoplay" is still a good choice, but both reasons given are wrong. WebKit now parses explicit origins, and BCD 'wildcards' means subdomain wildcard origins; Firefox and WebKit both support the '*' token. Valid reasons to avoid '*': any origin loaded in the frame would get the mic, and Firefox shows a two-origin prompt. Add 'screen-wake-lock' if Wake Lock is planned.
- ONBOARDING CHECK: the header check only matters for Chromium browsers. Firefox and Safari ignore Permissions-Policy headers. Keep the check, since Chrome is the majority, but word the error and diagnostics accordingly. Also check our own frame-ancestors per tenant.
- PERMISSION FLOW: 'Chrome and Safari attribute the request to the clinic's top-level site' is verified for Chrome only. For Safari it is inferred from WKWebView code, and Firefox shows both origins only with '*'. Phase 0 should screenshot the prompts.
- SIGNALLING and DATA CHANNEL: there is no need to write a new ~150-line client or to test whether audio-only works. The chosen template already ships an audio-only client and server-side SDP enforcement. The security boundary must be the server SDP policy, which rejects m=application, not browser code.
- CONNECTION STATE MACHINE: the 5 s grace copies the SDK transport, but the project's template uses 10 s. Choose one value on purpose. Both agree there is no ICE restart, so end-and-reconnect stays correct.
- NETWORK RESILIENCE: the 2026 sources point to a UDP-only relay answer, so do not assume TCP/443 exists. Consider waiting for ICE gathering (bounded at about 10 s, as in the official guide) and measure the effect on setup time in Phase 0.
- LATENCY (client): candidate-pair currentRoundTripTime is missing in current Safari per BCD. Fall back to remote-inbound-rtp roundTripTime. selectedCandidatePairId exists only from Firefox 153. Use inbound-rtp packetsReceived, not transport packetsReceived, for dead-connection detection, because Safari lacks the transport field.
- LATENCY (server): subtracting the silence duration from audio_end_ms only applies to server_vad. semantic_vad has no fixed silence_duration_ms, so the correction is undefined there.
- iOS HANDLING: the WebKit 282939 workaround sets 'auto' before getUserMedia and 'play-and-record' after it, then 'playback' and 'auto' at the end. That is not simply 'play-and-record around the call'. It is unverified inside a cross-origin iframe.

### Facts the fact-checker added

- The Permissions-Policy HTTP header only works in Chromium: Chrome 85, with microphone from 88. Firefox and Safari do not support it. A clinic header can block the widget only in Chrome, Edge and Android Chrome. In Firefox and Safari, only the iframe allow attribute and any ancestor iframes' allow attributes matter.
- Current WebKit (PermissionsPolicy.cpp) parses '*', 'self', 'src', 'none' and explicit origins in allow. WebKit bug 189901 is stale. WebKit also treats 'screen-wake-lock' as a policy-controlled feature, so a Wake Lock inside the iframe probably needs allow="screen-wake-lock".
- The project's own template (openai-agents-js examples/realtime-server-controlled) already provides: an audio-only browser client (src/client/audioOnlyWebRtc.ts) with echoCancellation, noiseSuppression and autoGainControl true, video false and no data channel; a server SDP policy that "accepts only offers and answers with exactly one non-rejected m=audio" (sdpPolicy.ts); and SSE delivery of allowlisted events to the browser. It uses a 10_000 ms disconnected grace, closes immediately on failed, and has no ICE restart or auto-reconnect. Its create-call request has a 15 s timeout, sends multipart sdp + session fields, uses redirect:'error', and validates Location against /v1/realtime/calls/(rtc_...).
- The template's server reads output_audio_buffer.started and stopped from the sideband (publicEventProjection.ts). So the sideband very likely receives these WebRTC-only events, which mostly answers that open question.
- The official OpenAI WebRTC guide (voice-webrtc.md) waits for ICE gathering, with a 10 s timeout in its sample, before posting the offer. The Agents SDK transport and the template do not wait.
- 2026 secondary sources describe the relay answer as one shared VIP and UDP port. Nothing confirms a TCP/443 candidate after the re-architecture, so the risk on networks that block UDP is higher than the 2025 webrtcHacks data suggests.
- OpenAI's docs now also describe a separate GPT-Live contract: POST /v1/live/sessions, attach at wss://api.openai.com/v1/live/sessions/{session_id}/attach, model gpt-live-1. The Realtime /v1/realtime/calls flow with a call_id sideband is still documented, with no deprecation notice.
- Safari gaps per BCD: candidate-pair currentRoundTripTime removed in Safari 16.2; inbound-rtp audioLevel removed in 16.3 and absent on iOS; transport packetsReceived not supported. Use remote-inbound-rtp roundTripTime (Safari 14.1+) and inbound-rtp packetsReceived instead.
- Our widget origin must allow framing by each clinic origin: CSP frame-ancestors per tenant, and no X-Frame-Options DENY or SAMEORIGIN. The clinic's CSP frame-src must allow our origin. Not researched here.
- Whether navigator.audioSession works from inside a cross-origin iframe on iOS has not been researched.

## 5. Agents SDK server-controlled pattern for the voice worker

### Verdict (researcher)

The realtime-server-controlled example matches our architecture almost exactly and can serve as the base for the worker. The flow is: browser sends an audio-only offer to our server; the server enforces the SDP policy; it creates the call with a multipart POST to /v1/realtime/calls using a standard key and OpenAI-Safety-Identifier; it parses the rtc_ ID from Location under strict checks; it creates a RealtimeSession with transport 'websocket' and connect({apiKey, callId}); it returns the answer SDP only after a session.updated that contains our instructions and tools. Cleanup is idempotent and ends in calls.hangup.

The example cannot ship as-is for six reasons:
(1) It leaves tracing at 'auto'. We must set tracingDisabled:true and preferably tracing:null in the /calls body. The OPENAI_AGENTS_DISABLE_TRACING env var is not read by agents-realtime 0.21.0.
(2) The model is one global value, and the SDK falls back to 'gpt-realtime-2.1' in every session.update unless options.model is set. The per-tenant model must go into both the /calls body and the RealtimeSession.
(3) All state is in memory with a 30-minute sweep. We need Postgres-backed call rows, recovery on startup, and a 10-minute deadline with a graceful wrap-up.
(4) The readiness check compares against one static agent. It must compare against the instructions and tools built for each call.
(5) On a sideband attached to a WebRTC call, the stock websocket transport's interrupt() is very likely a no-op: it needs audio deltas, which per a forum report do not reach the sideband. An audio guardrail trip would then not stop playback. We must send response.cancel and output_audio_buffer.clear ourselves, ideally through a small transport subclass like OpenAIRealtimeSIP.interrupt.
(6) The BFF and the agent share one process. We split them: Next.js handles auth, tenant lookup and SDP policy, then calls an internal worker endpoint that owns the call and sideband lifecycle.

Tools map cleanly to tool() with zod, timeoutMs, error_as_result and trusted runContext.context. We should not use needsApproval, because the server has no human to approve. Per-response usage should be stored from the raw response.done events rather than from SDK aggregates.

### Design recommendations (researcher)

- Process split: the Next.js web process owns all public HTTP; the worker exposes only an internal API. Next.js route POST /api/widget/voice/session (Content-Type application/sdp) does five things: (1) check the widget token, a short-lived signed JWT minted for the iframe with tenantId/clinicId/visitorId claims; (2) check Origin against that clinic's allowlist and apply per-IP/per-tenant rate limits; (3) require X-Voice-Session-Id (UUIDv4, generated in the browser as in the example's X-App-Session-Id); (4) run assertAudioOnlySdp (copy sdpPolicy.ts unchanged into a shared package) and the 256 KiB cap; (5) forward {tenantId, clinicId, voiceSessionId, offerSdp, safetyIdentifier} to the worker at POST http://<private-ip>:<port>/internal/calls, authenticated with an HMAC header. The worker runs VoiceController.start and returns the answer SDP. Keep the readiness gate, so Next.js returns the answer only after session.updated confirms the agent config. Mirror the example's other routes as Next.js proxies to the worker: GET /events as SSE (or Postgres LISTEN/NOTIFY) and POST /close. The example's CSP frame-ancestors 'none' still suits the JSON/SDP API responses, but the iframe widget page needs frame-ancestors set to the clinic origins and an iframe allow="microphone".
- Per-call call creation (adapting realtimeCall.ts). Look up the tenant to get model ('gpt-realtime-2.1-mini' or the per-clinic fallback 'gpt-realtime-2.1') and voice, and use the same values in the /calls session JSON AND in new RealtimeSession(agent, { model, ... }). Without the model option the SDK sends 'gpt-realtime-2.1' in every session.update. Send tracing:null in the /calls session so tracing is never on at any point. Better still, build the whole session from the SDK so instructions, tools, transcription, turn detection, tracing and truncation are present from the first packet: const cfg = await RealtimeSession.computeInitialSessionConfig(agent, sessionOptions); const payload = new OpenAIRealtimeWebSocket().buildSessionPayload(cfg); form.set('session', JSON.stringify({ ...payload, tracing: null })). Confirm in Phase 0 that /calls accepts the full payload. Keep redirect:'error', AbortSignal.timeout(15_000), the strict Location regex and answer-SDP validation exactly as in the example. Derive the safety identifier as HMAC-SHA256(server_secret, `${tenantId}:${visitorId}`) in hex: stable and privacy-preserving, never sent from the browser.
- RealtimeSession options for the sideband: new RealtimeSession<CallCtx>(agent, { model, transport: new SidebandTransport(), tracingDisabled: true, historyStoreAudio: false, context: { tenantId, clinicId, voiceSessionId, callId, locale, tz: 'Asia/Dubai' }, config: { outputModalities: ['audio'], audio: { input: { transcription: { model: 'gpt-live-transcribe' /* or gpt-transcribe */, languages: ['ar','en'] }, turnDetection: { type: 'semantic_vad' /* or server_vad, as in the example */, createResponse: true, interruptResponse: true } }, output: { voice } }, providerData: { truncation: { type: 'retention_ratio', retention_ratio: 0.8 } } }, outputGuardrails, outputGuardrailSettings: { debounceTextLength: 100 } }). Set OPENAI_AGENTS_DISABLE_TRACING=1 as well, but do not rely on it for realtime: 0.21.0 does not read it.
- SidebandTransport: write a small subclass so interrupt() works on a sideband attached to a WebRTC call, modelled on OpenAIRealtimeSIP.interrupt: class SidebandTransport extends OpenAIRealtimeWebSocket { override interrupt(cancel = true) { if (this.status !== 'connected') return; if (cancel) this._cancelResponse(); this.sendEvent({ type: 'output_audio_buffer.clear' }); } override sendAudio(): never { throw new Error('audio flows over WebRTC'); } }. This makes the SDK's built-in guardrail path (this.interrupt()) actually cut playback. Phase 0 should check two things: that the base class calls interrupt(false) on every input_audio_buffer.speech_started, which would send an extra output_audio_buffer.clear (if that causes error events, ignore speech_started-triggered calls with a flag); and that output_audio_buffer.cleared arrives after a forced trip. Alternative: keep transport 'websocket' and in session.on('guardrail_tripped') send transport.sendEvent({type:'response.cancel'}) and then {type:'output_audio_buffer.clear'} yourself.
- Readiness gate per tenant: generalise sidebandReady.ts so it compares against the instructions string and tool names computed for THIS call (the example compares against one static voiceAgentConfiguration). Also treat it as a failure if session.updated echoes tracing !== null. Keep the 10 s timeout. On timeout, close the session and hang up the call (the example already does both in the VoiceController catch block).
- Tools (8): one tool<typeof P, CallCtx>() each, with zod parameters (strict by default). Domain rules: phone as z.string().regex for E.164 UAE; dates as ISO strings validated server-side in Asia/Dubai; optional fields as .nullable() rather than .optional(). Each tool sets timeoutMs (about 4000 for reads such as get_clinic_info/find_slots/find_booking, about 8000 for writes) and timeoutBehavior:'error_as_result' with a timeoutErrorFunction that returns JSON such as {ok:false, code:'TIMEOUT', say:'...'}. execute(input, runContext, details) takes tenantId/clinicId ONLY from runContext.context and passes details.signal to the database/PMS client. Return compact JSON strings (toSmartString serializes objects). Make writes idempotent with details.toolCall.callId as the idempotency key in Postgres. Do not use needsApproval: the server has no human approver, and a pending approval stalls the agent. Enforce spoken confirmation in the flow instead: hold_slot returns a holdId with a TTL; book_appointment/reschedule/cancel require a holdId or bookingId that the server verifies belongs to this call's context. Set an explicit errorFunction that logs internally and returns a bilingual-safe generic message.
- Usage and cost: in session.on('transport_event'), for e.type==='response.done', insert one row per response {voice_session_id, tenant_id, response_id, status, model, usage jsonb = e.response.usage}. That keeps cached/audio/text splits, which SDK aggregates flatten into arrays, and the SDK recomputes total_tokens. Also store e.usage from conversation.item.input_audio_transcription.completed as transcription usage. On close, write session.usage (requests, inputTokens, outputTokens) as a cross-check. Never forward usage to the browser (as in the example).
- Guardrails on transcripts: implement a fast deterministic guardrail (no medical advice, no other clinic's data, no PII readback beyond policy) with policyHint. If you use an LLM classifier, use OpenAI only, with a timeout, and run it with debounceTextLength around 100. On 'guardrail_tripped': make sure response.cancel and output_audio_buffer.clear are sent (via the SidebandTransport above), record the event in Postgres, and tag the SDK's injected feedback message (a USER-role item starting '⚠️ Your last answer was blocked.') so it is excluded from patient-facing transcripts. If that feedback wording is unacceptable, skip the SDK outputGuardrails and implement the same debounce yourself on response.output_audio_transcript.delta, sending response.cancel, then output_audio_buffer.clear, then a system conversation.item.create, then response.create.
- Context injection: for silent context (clinic hours refresh, a 'time is almost up' note), use session.transport.sendEvent({ type: 'conversation.item.create', item: { type: 'message', role: 'system', content: [{ type: 'input_text', text }] } }). That adds no response.create. Use session.sendMessage only when you want an immediate spoken reply, since it always triggers one. For history, keep session.history only in memory, filter transcripts into Postgres as they arrive (30-day TTL job), and never store audio (historyStoreAudio false is the default).
- 10-minute cap, replacing the example's 30-minute sweep. Add a per-call deadline (created_at + 10 min) stored in Postgres, with in-process timers: at 9:00 inject a system message asking the agent to wrap up (no response); at about 9:45, if the agent is not speaking, send response.create with instructions for a short bilingual goodbye; at 10:00 or on output_audio_buffer.stopped after the goodbye (whichever comes first, with a hard 10:15 limit), run sessions.close(id): realtimeSession.close(), then calls.hangup(callId). Keep a 30 s sweep that closes rows past deadline + grace and retries failed hangups. Lower maxSessions to the planned capacity (e.g. 60 per worker for a 50-concurrent target) and add a per-tenant concurrent cap. On 503, offer request_callback in the widget.
- Move state to Postgres: the example's SessionManager is in-memory only, and its #cancelledSetups grows without limit. Table voice_sessions(id uuid pk = browser session id, tenant_id, clinic_id, visitor_hash, openai_call_id unique null, model, voice, state enum(reserved, creating, active, closing, closed, failed), created_at, deadline_at, closed_at, close_reason, hangup_confirmed_at, worker_id). Partial unique index on (visitor_hash) WHERE state IN ('reserved','creating','active') replaces the one-session-per-owner Map. Table voice_session_cancellations(id, tenant_id, created_at) with a TTL longer than the setup replay window. Write openai_call_id as soon as Location is parsed, before the sideband. On worker start, hang up every call owned by this worker_id that has no hangup_confirmed_at (the example cannot do this after process death). Treat a hangup NotFoundError as success, as the example does.
- Shutdown for the worker: on SIGTERM, stop accepting (reserve() throws, health/readiness goes false so Next.js returns 503), then drain. Either let active calls run to their 10-minute deadline (set the container stop timeout above 10 min), or hang up immediately after a short spoken notice. Then run the example's closeAll() behaviour (one bounded hangup retry, log without payloads), and mark rows closed in Postgres. Keep openai client settings {timeout:10_000, maxRetries:0} for hangup, since retries are driven by the sweep.
- Browser events: reuse the example's allowlisted projection (listening/thinking/speaking/idle, VOICE_* error codes, session.ready/closed) and add app.call.time_warning and app.call.ended {reason: 'time_limit'\|'agent_end'\|'error'\|'capacity'}. Do not forward transcripts, tool calls, callId or usage. Reuse AudioOnlyWebRtc in the widget: no data channel, 10 s disconnected grace, cleanup on 'failed' or mic end. Also reuse the example's client rules: generate the session ID before the SDP, and the close endpoint records a cancellation even before setup finishes.
- Phase 0 checks to add to the Block 2 test plan. (a) Is response.output_audio.delta absent on the sideband, which would make the stock websocket interrupt() a no-op? (b) Does session.created arrive on the sideband? (c) Does the session.updated echo show tracing:null? (d) Does /calls accept the full session payload (instructions/tools/tracing/truncation)? (e) Does output_audio_buffer.clear plus response.cancel actually cut audio mid-sentence in Arabic, and how fast? (f) Do the audio.input/output.format fields the SDK sends cause errors on a WebRTC call? (g) Does closing only the sideband WS end the WebRTC call, or is hangup always required?

### Fact-check: the verdict holds

I re-checked the claims against the example source on main (unchanged since 2026-10-09), the agents-realtime and agents-core source at the 0.21.0 tags, the SDK docs, and the OpenAI API docs and reference. The main architecture claims hold: the SDP policy, the multipart /v1/realtime/calls request with OpenAI-Safety-Identifier, the strict Location parsing, the call_id sideband URL, the session.updated readiness gate, the cleanup that always ends in hangup, the tracing 'auto' default on session.created, the fallback to gpt-realtime-2.1 when model is not set, the usage shapes, the guardrail behaviour, and the fact that the stock websocket interrupt() depends on audio deltas.\n\nCorrections are minor:\n- The sidebandReady test does not prove the real order of the two session.update messages.\n- #cancelledSetups is cleared in closeAll().\n- The agent instance is created per session; only its configuration is static.\n- The 60-minute limit comes from realtime-conversations.md and the SDK build guide, not the hangup reference.\n- The 'docs bug' about errorFunction is ambiguous wording that refers to the outputSchema case.\n- The community-thread quote is a paraphrase from a non-staff user.\n- calls.create does not document a full session schema.\n- gpt-transcribe in a Realtime session requires WebSocket audio.\n\nThe interrupt() no-op on the sideband is consistent with the code but still unverified, and needs a Phase 0 test. On the design side:\n- The Origin-allowlist check is wrong for an iframe widget.\n- Sending the full SDK payload to /calls rests on unverified schema support.\n- gpt-transcribe should be dropped.\n- The custom SidebandTransport can be replaced by the existing OpenAIRealtimeSIP class.\n\nNone of these overturn the verdict: the example is a sound base, and the six listed adaptations are needed and correctly identified.

### Problems with the recommendations (fact-checker)

- Process split, step 2 ('check Origin against that clinic's allowlist'): this conflicts with the iframe architecture. Requests made from inside our iframe carry the widget's own origin, not the clinic page's origin. Clinic-origin control has to come from per-clinic CSP frame-ancestors on the widget page and from how the widget token is minted. On the API, check Origin == our widget origin.
- Call creation ('Better still, build the whole session from the SDK ... form.set(session, {...payload, tracing:null})'): this rests on unverified facts. calls.create does not document a full session schema. buildSessionPayload always adds audio.input/output.format pcm 24 kHz and the model. The SDK's SIP helper notes that the Calls API rejects some turn_detection fields for SIP. Keep the minimal example body as the default and adopt the full payload only after Phase 0 checks (d) and (f) pass.
- RealtimeSession options suggest transcription 'gpt-live-transcribe /* or gpt-transcribe */'. The docs say gpt-transcribe in a Realtime session is a committed-turn workflow that 'requires a WebSocket connection', and our audio is WebRTC. Use gpt-live-transcribe with languages:['ar','en'] only (no 'language'), and check in Phase 0 that it works inside a gpt-realtime-2.1-mini conversation session.
- SidebandTransport: a custom subclass is not needed. Use the exported OpenAIRealtimeSIP, or subclass it, because it already has the same interrupt/sendAudio behaviour. If the override is kept, note that it skips the base _interrupt path, so 'audio_interrupted' is never emitted. The Phase 0 check on whether interrupt(false) runs on every speech_started is already answered from the source: it does when interrupt_response is true.
- Readiness gate ('treat it as a failure if session.updated echoes tracing !== null'): no doc shows what tracing looks like in the echo (null, absent or 'auto'). A strict !== null check could fail healthy calls. Log or alert on any non-null value until Phase 0 confirms the echo shape.
- Usage ('SDK aggregates flatten into arrays'): this wording is imprecise. The SDK keeps one TokenDetails entry per response in the arrays, nested cached details included. What it loses is the link to response_id, status and model, and it recomputes total_tokens. Storing raw response.done usage is still the right call.
- Guardrails: the SDK feedback message sends JSON.stringify(outputInfo) to the model as user content. Keep outputInfo free of PII and internal details, or use the custom-debounce alternative described in the recommendation.
- Tools: details.signal only exists when timeoutMs is set, because Realtime passes details={toolCall}. That is fine since every tool sets timeoutMs, but the DB/PMS client code must handle an undefined signal if a timeout is ever removed.
- SDK tracing env var: setting OPENAI_AGENTS_DISABLE_TRACING=1 is harmless. The recommendation is right not to rely on it, because agents-realtime 0.21.0 never reads it even though the tracing guide says it works for RealtimeSession.

### Facts the fact-checker added

- OpenAIRealtimeSIP is exported from @openai/agents-realtime 0.21.0. It extends OpenAIRealtimeWebSocket, requires callId and uses the same ?call_id= URL. Its interrupt() sends response.cancel (if asked) then output_audio_buffer.clear, and sendAudio() throws. It already does what the proposed SidebandTransport would do, and nothing in its connect path is SIP-specific (openaiRealtimeSip.ts).
- The base websocket transport calls this.interrupt(!interrupt_response) on every input_audio_buffer.speech_started, reading interrupt_response from the server's session.updated echo. With interruptResponse:true, a SIP-style transport therefore sends output_audio_buffer.clear on each speech_started. OpenAI's own SIP transport behaves this way, so that Phase 0 question is already answered from the source.
- The SDK never puts tracing in the regular session.update payload ('We don't set tracing here'). Tracing is sent only from the session.created handler, so if session.created never reaches a sideband, the SDK sends no tracing update at all.
- The guardrail feedback message sent to the model includes 'Failure Details: <JSON of outputInfo>' as well as policyHint (guardrail.ts). outputInfo must not contain PII or internal data.
- The transcription guide says gpt-transcribe in a Realtime session 'requires a WebSocket connection'. gpt-live-transcribe uses 'languages' and not 'language' (do not send both). Unsupported language codes are rejected. delay is documented as only supported with gpt-realtime-whisper in GA Realtime sessions.
- The calls.create API reference shows only {type, model} in the session part and gives no session schema. The full schema (tracing, truncation, transcription, etc.) is documented on calls.accept and session.update only.
- OpenAIRealtimeSIP.buildInitialConfig states that the Calls API rejects turn_detection threshold, prefix_padding_ms and silence_duration_ms for SIP sessions. That matters if we send a full server_vad config to /v1/realtime/calls.
- The 60-minute Realtime session limit is in realtime-conversations.md and the SDK build guide, not the hangup reference.
- Deprecations page: /v1/realtime/calls is not listed for deprecation. gpt-realtime-2.1-mini is the named replacement for older realtime-mini and TTS models (removal Jan 6 and Jan 20, 2027), which supports the model choice. The Realtime Beta interface was removed 2026-05-12.
- RealtimeSession has a toolErrorFormatter option. In 0.21.0 it formats approval-rejection messages only, not execute() errors.
- The example also exposes GET /health and GET /api/auth/session. Its safety identifier is sha256(ownerId) hex (demoAuth.ts), and the README tells you to replace it with a stable, privacy-preserving production identifier.
- The calls.create reference's sample answer SDP contains m=application. That happens because the sample offer had a data channel. For an audio-only offer the answer should have audio only, and the example's answer validation enforces that.

### Open questions

- Does a Realtime WebRTC call's sideband (wss://api.openai.com/v1/realtime?call_id=...) ever receive response.output_audio.delta? A community thread (secondary) says no. If confirmed, the stock OpenAIRealtimeWebSocket.interrupt() and the SDK's audio-guardrail interrupt do nothing on our sideband. Needs a Phase 0 test.
- Does the server send session.created to a sideband connection on attach? The SDK's tracing update is triggered by session.created, and the example test simulates it, but no API doc states it.
- Does POST /v1/realtime/calls accept the full session object (instructions, tools, tracing:null, truncation, audio.input.transcription) in the 'session' multipart field? The docs example shows only {type, model, audio.output.voice}. The full schema is documented for /calls/{id}/accept (SIP).
- Is sending audio.input.format / audio.output.format (pcm 24 kHz, always included by the SDK in session.update) harmless on a WebRTC call? The GPT-Live docs say to omit audio.format for WebRTC; the Realtime docs say nothing about it.
- Does closing only the sideband WebSocket end the WebRTC call, or does the call keep running and billing until hangup or a browser disconnect? The example always calls hangup explicitly; there is no doc statement.
- Is an extra output_audio_buffer.clear harmless when nothing is playing? It would be sent on every speech_started if we use OpenAIRealtimeSIP or a subclass that does not filter those calls.
- Does gpt-realtime-2.1-mini support reasoning.effort and the gpt-live-transcribe / languages:['ar','en'] transcription options? The SDK types allow them, but model support was not checked here.
- OpenAI's voice docs now lead with GPT-Live (POST /v1/live/sessions, /attach sidebands, session.close/session.closed with final usage, a 15 s WebRTC initialization charge). Is the Realtime /v1/realtime/calls path on a deprecation timeline? That affects how long the decided architecture stays supported.
- The SDK tools guide says the default errorFunction is 'disabled so the original error is rethrown', but the 0.21.0 source returns 'An error occurred while running the tool. Please try again.' when there is no outputSchema. Is that a docs bug? Set errorFunction explicitly either way.

## 6. Phase 0 evaluation method

### Verdict (researcher)

Recommendation: build a custom TypeScript harness on Playwright and real Chromium (new headless mode) that drives the real widget iframe.

**How the harness works**
- **Caller audio:** inject it by overriding getUserMedia with a Web Audio stream. Chrome's `--use-file-for-fake-audio-capture` flag gives one WAV per browser launch, loops unless `%noloop` is added, rejects 24-bit PCM and gives no timing control. Keep that flag only for a small smoke test of the real microphone path.
- **Agent audio:** capture it in the same AudioContext, so turn latency (end of caller speech to first agent audio, as OpenAI's cookbook defines it) is measured on one clock to within a few milliseconds. Split latency into parts using the voice worker's sideband events and getStats.

**Test stages (OpenAI's crawl, walk, run method)**
- **Crawl:** single turns from TTS fixtures, with deterministic tool grading.
- **Walk:** human recordings from native Gulf speakers, as the reality anchor.
- **Run:** scripted multi-turn calls plus agent-versus-agent calls, where a second gpt-realtime-2.1 session plays the caller.

**Deadline for caller audio:** gpt-4o-mini-tts and the other TTS models shut down on 6 January 2027 (official deprecations page), and the named replacement, gpt-realtime-2.1-mini, cannot serve /v1/audio/speech. Generate the full fixture library now. Write the Arabic text in Gulf dialect spelling and have a native speaker screen every clip, because accent instructions alone are unreliable and there is no evidence on Gulf dialect quality.

**Statistics**
- At an observed 85% success rate, the Wilson 95% intervals are [70.9%, 92.9%] at N=40, [75.6%, 91.2%] at N=80 and [77.5%, 90.3%] at N=120.
- Showing the rate is above 75% against 85% needs about 103 calls (one-sided α = 0.05, 80% power). Comparing two configurations needs about 250 per arm.
- Proposed sizes: 120 Arabic calls, 80 English and 40 code-switched, with the gate "Wilson lower bound at least 75% and point estimate at least 85%" applied to Arabic and English, and zero critical booking errors across all 360 calls.

**Human evaluation**
- P.800 ACR quality and listening-effort scales, plus a custom dialect-authenticity scale.
- 20 Gulf Arabic raters and 12 English raters, 40 clips per condition, with anchors and attention traps.
- Agreement measured with Krippendorff's alpha (ordinal, at least 0.667) and ICC (CI lower bound at least 0.75).
- Expect results from synthetic and agent-versus-agent tests to be optimistic. Use the human-recorded Walk set and manual calls as the final release gate.

### Design recommendations (researcher)

- HARNESS ARCHITECTURE: build the harness in-house in TypeScript on Node 24 with Playwright Test, which keeps every AI component on OpenAI. Run the real host page and the real widget iframe against the real Next.js app and voice worker in a staging tenant. Put a deterministic mock clinic backend behind the 8 tools, seeded per scenario with fixed slots, existing bookings and clinic info. Give the voice worker a test-only hook that logs each tool call and its arguments, sideband server events with timestamps (input_audio_buffer.speech_stopped, output_audio_buffer.started/stopped/cleared, response.done) and the final mock-DB state for each call ID. Use new headless mode (`channel: 'chromium'`), not the headless shell. Run about 10 browsers in parallel from a machine in the UAE, or on a UAE consumer ISP, so the round trip to OpenAI is realistic.
- AUDIO INJECTION, primary method: do not use `--use-file-for-fake-audio-capture` for multi-turn tests. It allows one file per browser launch, loops unless you add %noloop, and gives you no control over timing. Instead, call `context.addInitScript` (it also runs in the widget iframe) to replace `navigator.mediaDevices.getUserMedia` with a stream from a `MediaStreamAudioDestinationNode` in a page-owned AudioContext at 48 kHz. Use `exposeBinding` so the runner can push each caller turn as PCM and schedule it with `AudioBufferSourceNode.start(when)`. Grant the 'microphone' permission. First check that the override still works when fake-device flags are absent. Caveat: this bypasses Chrome's echo cancellation, noise suppression and gain control, which differs from production.
- AUDIO INJECTION, secondary smoke test: keep a small suite (5 calls per language) that uses the real getUserMedia path with the production constraints. Launch Chromium with `--use-fake-ui-for-media-stream --use-fake-device-for-media-stream --use-file-for-fake-audio-capture=<file>.wav%noloop`, using one browser per file. Use a mono 16-bit PCM WAV at 48 kHz with leading silence, and avoid 24-bit because the parser rejects it. This proves the real microphone and audio-processing path works.
- OUTPUT CAPTURE: when the remote track arrives, attach it to a muted, playing `<audio>` element (the reported Chrome workaround). Feed the same stream into a `MediaStreamAudioSourceNode` in the same AudioContext, then into an AudioWorklet that computes RMS per 10–20 ms frame stamped with `currentFrame`. Also write a stereo test WAV with the caller on the left and the agent on the right. These recordings contain only synthetic or consented test audio and live in the test store, outside the production 'no audio stored' policy. Transcribe the agent channel offline with gpt-transcribe, using language hints ['ar','en'], for grading.
- TURN LATENCY: define it as the end of caller speech to the first agent audio, as in the OpenAI duplex cookbook and τ-Voice. Precompute the caller speech end per fixture offline with an energy VAD on the trimmed WAV, so it equals the scheduled start plus the speech-end offset on the AudioContext clock. The agent start is the first frame above −45 dBFS that is followed by at least 60 ms of continuous energy. Because both points are on one clock, the timing error is a few milliseconds. Split latency into parts using sideband speech_stopped and output_audio_buffer.started, plus the getStats jitterBufferDelay/jitterBufferEmittedCount delta. Report p50, p90 and p95 per language, kept separate for turns with tool calls and turns without. Count any turn with no agent audio within 5,000 ms as a non-response, matching the cookbook's default deadline.
- BARGE-IN TESTS: in 15% of RUN scenarios, schedule a caller interruption 1.0–2.0 s after agent speech starts. Measure yield latency (from caller speech start until agent RMS drops below threshold) and yield rate (agent stops within 2 s, as in τ-Voice). Confirm each yield with output_audio_buffer.cleared on the sideband. Also add 10 backchannel probes per language ('اوكي', 'ايه', 'mm-hmm'); the agent should not restart or stop its turn, since τ-Voice found OpenAI selectivity to be weak.
- MULTI-TURN SEQUENCING, Mode A (scripted, reproducible): each scenario has an ordered list of caller-turn fixtures and gives all needed information up front, so no branching is required. The next turn plays 400–800 ms (randomised with a seed) after the agent's turn ends. A turn ends when output_audio_buffer.stopped arrives from the worker hook, or after 1.2 s of agent silence. If the agent asks something the script cannot answer, the run is labelled 'script-divergence' rather than a failure, then reviewed.
- MULTI-TURN SEQUENCING, Mode B (agent vs agent): run a second OpenAI Realtime session in Node over WebSocket as the simulated caller, using gpt-realtime-2.1 with audio/pcm at 24 kHz and semantic_vad. Pipe its output audio, resampled from 24 to 48 kHz, into the page's injected stream. Pipe the captured agent audio, resampled from 48 to 24 kHz, into the caller session with input_audio_buffer.append. Model the caller prompt on the cookbook's scenarios.json: goal, known_facts, agenda and persona. The persona specifies Emirati or Gulf dialect, code-switching habits and impatience level, and hidden expectations stay off the agent side. End the call when an OpenAI judge model confirms resolution, with a 4-minute cap. Version-pin the simulator prompt. Treat Mode B results as optimistic, because OpenAI is talking to OpenAI with clean audio and a non-native-sounding dialect. gpt-live-1 is a possible later caller, but it is on a different API and its Arabic support is unverified.
- SYNTHETIC CALLER AUDIO: generate the whole Crawl and Mode A fixture library now with gpt-4o-mini-tts, because it shuts down on 6 Jan 2027. Request response_format wav or pcm at 24 kHz and use all 13 voices for speaker variety. Write the input text in Gulf dialect spelling (for example أبي أحجز موعد / باچر / شلون), because accent instructions alone are unreliable. Add instructions such as 'Speak as a native Emirati Arabic speaker, casual phone register, natural pace'. A native Emirati reviewer accepts or rejects every Arabic fixture for dialect plausibility; keep only accepted fixtures and report the rejection rate. After January 2027, produce new fixtures through a gpt-realtime-2.1(-mini) 'read this script verbatim' session, checked by a gpt-transcribe round-trip with a character error rate below 10%. Add seeded, deterministic acoustic variants: clean, café noise at 15 dB SNR, laptop-mic EQ and 2% Opus packet loss.
- HUMAN-RECORDED WALK SET, the reality anchor: 10 native Gulf Arabic speakers (at least 6 Emirati, mixed gender and ages) and 6 English speakers (UAE residents with mixed accents: South Asian, Arab, Filipino and Western). Each records 15 single-turn requests plus 2 scripted full calls on their own phone or laptop browser, with written consent and no patient data. If the TTS-based results are more than 10 points better than the WALK results, the synthetic suite is too optimistic and must not be used as the release gate on its own.
- SCENARIO COUNTS for Phase 0 per model configuration. CRAWL (single turn, VAD off, deterministic tool and argument grading): 100 Gulf Arabic, 60 English and 40 code-switched utterances. WALK: about 150 Arabic and 90 English recorded clips. RUN end-to-end (Modes A and B mixed about 50/50): 60 Arabic, 40 English and 20 code-switched scenarios, each run twice on gpt-realtime-2.1-mini (240 calls), and once on gpt-realtime-2.1 for the per-clinic fallback (120 calls). Spread intents roughly as follows: booking 35%, reschedule 15%, cancel 15%, find booking 10%, clinic info 10%, callback 5%, negatives and out-of-scope 10% (medical advice, prices not in the knowledge base, another clinic). Overlays: 15% barge-in, 20% noisy, and at least 10% where the slot is unavailable or a hold expires. MANUAL: 20 real calls per language by staff on real devices.
- TASK-SUCCESS GRADING: each RUN call passes only if four things hold. (1) The final mock-DB state equals the expected state. (2) The required tool calls happened, with arguments matched after normalisation, as in the cookbook's deterministic tool_accuracy. (3) No unauthorised or extra write happened. (4) An OpenAI LLM judge, given the transcript and tool trace, confirms the agent read back the date, time, doctor and patient name, and stated no invented policy. Before trusting the judge, calibrate it against 60 calls labelled by humans (30 in Arabic) and require Cohen's kappa of at least 0.7. Separately, count CRITICAL errors: wrong slot, date or patient committed; booking without confirmation; cancelling the wrong booking; or medical advice.
- PASS/FAIL STATISTICS: gate each language separately. Arabic (N=120 calls) passes if the Wilson 95% lower bound is at least 75% and the point estimate at least 85%, which means at least 100 of 120. At a true 85% the gate passes about 74% of the time; at a true 75% it passes about 2% of the time. English (N=80) needs at least 68 of 80. The code-switch figure (N=40, CI about ±11 points) is a diagnostic only. Critical errors must be zero across all 360 RUN calls (exact one-sided 95% upper bound below 1%). Because the 2 runs per scenario are correlated, compute CIs with a scenario-level cluster bootstrap as well as Wilson, and also report pass^2 per scenario. To compare the mini model with the full model, use a paired McNemar test on the same scenarios. Phase 0 can only detect differences of roughly 15 points or more, so do not read a non-significant result as 'equivalent'.
- LATENCY AND INTERACTION GATES (provisional, to be aligned with the Block 2 latency budget): for turns without tool calls, p50 ≤ 1.2 s and p90 ≤ 2.0 s. For turns with tool calls, p90 ≤ 3.0 s, with a spoken preamble allowed to count as first audio. At least 98% of turns answered within 5 s. Barge-in yield rate at least 90% within 2 s. Agent interruptions of the caller at most 10% of turns. Report each separately for Arabic and English, because semantic_vad may wait longer on Arabic trailing speech. Run a 1,000-turn sample per language so p90 has a tight bootstrap CI.
- HUMAN EVALUATION OF NATURALNESS AND DIALECT: recruit 20 native Gulf Arabic raters (at least 12 Emirati) and 12 English raters (UAE residents). Stimuli per language and model are 40 agent-turn clips of 5–12 s, balanced across scenarios and taken from RUN recordings. Add 4 anchors (2 high: a human Emirati receptionist recording; 2 low: TTS reading Modern Standard Arabic text, or a degraded clip) and 4 attention traps. Each rater rates every clip of their language in random order, in 2 sessions of 25 minutes or less, on three scales. Scale 1 is P.800 ACR listening quality (5 Excellent to 1 Bad). Scale 2 is the P.800 listening-effort scale. Scale 3 is a custom 5-point 'Dialect authenticity' scale with anchors (5 'sounds like a native Gulf speaker', 3 'understandable Arabic but clearly MSA or another dialect', 1 'foreign or unnatural'), labelled as not a P.800 scale. This yields about 800 Arabic votes per condition, well above the 60-vote and 30-listener guidance. Add 10 whole-call recordings per language rated for overall satisfaction.
- HUMAN-EVAL STATISTICS AND AGREEMENT: report MOS with a 95% CI (t-based, clustered by rater) and the full score distribution. Compare models with a Wilcoxon signed-rank test on per-clip means. Measure inter-rater agreement with Krippendorff's alpha (ordinal), targeting at least 0.667, and ICC(2,k) for the averaged scores, judging the 95% CI lower bound against the Koo and Li 'good' threshold of 0.75. Exclude raters who fail traps or rate the low anchor 4 or higher. Provisional gates: Arabic naturalness MOS ≥ 3.8 with CI lower bound ≥ 3.6, dialect authenticity ≥ 3.5 with CI lower bound ≥ 3.3, and listening effort ≥ 4.0.
- PRIVACY AND OPS: Phase 0 uses only synthetic and consented test audio, stored in an isolated test bucket with its own retention rules. Keep OpenAI tracing off and build grading from your own logs. If you use the OpenAI Evals API for audio grading, check that it is compatible with your planned ZDR set-up first, because it requires uploading files. Pin model IDs and prompt versions in every results file, and keep regression, discovery and holdout scenario sets as the OpenAI guide recommends.

### Fact-check: the verdict holds

The research is largely accurate. Most claims check out against primary sources: the Chromium source, Playwright docs, W3C webrtc-stats, the OpenAI deprecations, model and TTS pages, the cookbook READMEs and metrics contract, τ-Voice, τ-bench, Koo & Li, Wester, Naderi and NIST. I recomputed all the Wilson intervals and power figures and they match.

Five claims need correction:
- **Chromium bug IDs:** the forum threads do cite Chromium bugs (933677, 121673 and 687574), and the quoted 'muted but playing' sentence is not on either page.
- **VAD defaults:** the API reference does state 0.5/300/500 as defaults, and gives max timeouts for semantic_vad eagerness of 8 s, 4 s and 2 s.
- **Temperature thread:** it does not support 'voice/tone vary between sessions'.
- **Accent thread:** it does not support 'non-English output has an American accent'.
- **Cookbook target:** the duplex cookbook evaluates gpt-live-1 on /v1/live/sessions, not the Realtime API, so its metric definitions transfer but its code does not.

The overall verdict holds: a Playwright harness with real Chromium, getUserMedia injection, crawl/walk/run stages, generating the TTS fixtures before 6 Jan 2027, and Wilson-based gating.

Some design recommendations need fixing before adoption:
- **Pass/fail gate arithmetic:** 'Wilson LB ≥ 75% and point ≥ 85%' at N=120 requires ≥102 successes, not 100. That gate passes a true-85% agent only about 56% of the time, not 74%. English at N=80 passes only 58% of the time. Correlated repeat runs reduce power further.
- **Rater numbers:** the human-eval section says 20 Arabic and 12 English raters are 'well above the 30-listener guidance'. That is false: both are below Wester's more-than-30 threshold.
- **Evals API and ZDR:** this open question is now answered. /v1/evals and /v1/files are not ZDR-eligible.

### Problems with the recommendations (fact-checker)

- PASS/FAIL STATISTICS (and verdict): internal arithmetic error. The rule 'Wilson LB >= 75% AND point estimate >= 85%' at N=120 needs >=102/120, not 100 (100/120 = 83.3%). Recomputed with exact binomial: it passes a true-85% agent 56% of the time (not 74%) and a true-75% agent 0.6% (not 2%). The 74%/1.9% figures apply only to the Wilson-only rule. Choose one rule and restate its power.
- PASS/FAIL STATISTICS: the gates are low-powered. English N=80 (>=68) passes a true-85% agent only 58% of the time, and Arabic under the combined rule 56%. A 'true 85%' system fails release about half the time, so the gate really demonstrates about 90%. The binomial figures also assume i.i.d. calls, but 2 runs per scenario are correlated, so effective N and power are lower still. Either raise N, lower the bar, or state the gate as a 'demonstrate >75%' test without the 85% point requirement.
- Critical-error bound 'below 1% across all 360 RUN calls' pools two different model configurations (240 on mini, 120 on full). Per configuration, the exact one-sided 95% upper bound with zero errors is 1.24% (240) and 2.5% (120). Pooling is not meaningful for gating a single configuration.
- HUMAN EVALUATION: the statement that 20 Arabic and 12 English raters are 'well above the 60-vote and 30-listener guidance' is wrong for listeners. Wester et al. say stable significance needs MORE THAN 30 listeners, and both rater pools fall below that. Only the vote count (800 per condition) exceeds Naderi's 60-vote recommendation.
- AUDIO INJECTION: exposeBinding/exposeFunction expose a Node function TO the page (page calls Node). To push caller PCM from the runner into the page, use frame.evaluate (or have the page poll a binding). The mechanism as described has the wrong direction.
- BARGE-IN, MODE A turn-end and latency decomposition rely on output_audio_buffer.started/stopped/cleared arriving on the sideband WebSocket. These are documented as 'WebRTC/SIP Only', and OpenAI's server-controls guide (https://developers.openai.com/api/docs/guides/voice-server-controls) does not say the sideband receives them. Keep the audio-energy fallbacks primary until a spike confirms this.
- SCENARIO COUNTS / CRAWL: 'VAD off' cannot be driven by simply playing audio through the WebRTC widget. With turn_detection null, someone must send input_audio_buffer.commit and response.create, which requires a worker or sideband hook. The OpenAI cookbook crawl streams 20 ms chunks directly over a socket. The plan must say whether CRAWL bypasses the widget, which is a direct WebSocket harness that differs from the production path.
- Scope conflicts with the project context: Phase 0 is described as a small prototype run before building the real system. The harness assumes the real Next.js app, real widget iframe, staging tenant and 8-tool mock backend, plus 360 RUN calls, 16 recording speakers and 32 raters. Consider a reduced Phase 0 tier (Arabic quality and latency) and move the full gate to a later phase.
- Secondary smoke test with the real getUserMedia path and file input: the Chromium source comment says you 'should disable audio processing (lest your audio file will play back distorted)'. With production AEC/NS/AGC on, expect distortion. Use the smoke test only for pipeline pass/fail, not for quality or latency numbers.
- TURN LATENCY: claiming 'a few ms' error is optimistic when onset is detected on 10–20 ms RMS frames, because resolution is about the frame length. Also, semantic_vad eagerness 'low' has an 8 s max timeout, which can exceed the 5,000 ms non-response deadline. Pin eagerness (or use server_vad) for gated runs. Note too that speech_stopped audio_end_ms includes the silence window.
- PRIVACY AND OPS: the open question is resolved. /v1/evals and /v1/files are NOT ZDR-eligible (retained 'Until deleted'), while /v1/realtime, /v1/audio/speech and /v1/audio/transcriptions are ZDR-eligible. Restrict any Evals API use to synthetic, non-patient data, or grade locally.
- Harness set-up gaps: a page-owned AudioContext created without a user gesture starts 'suspended' (Chrome autoplay policy). Use --autoplay-policy=no-user-gesture-required or a scripted click. A cross-origin widget iframe needs allow="microphone" (and allow="autoplay" for sound) on the host page, so the test host page must mirror the clinic embed code.
- Expectations borrowed from τ-Voice (weak selectivity, latency about 0.9 s) were measured on gpt-realtime-1.5 in English only, not on gpt-realtime-2.1(-mini) or Arabic. Treat them as priors, not targets.
- MODE B / cookbook reuse: the duplex cookbook's harness targets gpt-live-1 on /v1/live/sessions. Only its metric definitions and scenario schema carry over to a Realtime-based agent, not its code. The Realtime-specific reference harness is openai-cookbook examples/evals/realtime_evals.

- The duplex voice-agent cookbook's evaluated assistant defaults to gpt-live-1 via the GPT Live WebSocket /v1/live/sessions, not the Realtime API (https://raw.githubusercontent.com/openai/openai-cookbook/main/examples/audio/duplex_voice_agent_evaluation/README.md).

- Chrome autoplay policy: an AudioContext created before a user gesture starts suspended; --autoplay-policy=no-user-gesture-required disables this for tests. Cross-origin iframes need allow delegation (https://developer.chrome.com/blog/autoplay). The microphone permission policy's default allowlist is 'self' (https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Permissions-Policy/microphone).
- gpt-realtime-2.1-mini rate limits are published as RPM/TPM per tier (Build 400 RPM / 200k TPM), which matters when running ~10 parallel browsers plus Mode B caller sessions (https://developers.openai.com/api/docs/models/gpt-realtime-2.1-mini).

- The TTS guide is internally inconsistent about the voice count: 11 in the intro, 13 in the voice section (https://developers.openai.com/api/docs/guides/text-to-speech).

### Open questions

- I could not extract the full text of ITU-T P.800 Annex B (B.4.4 Listeners, B.4.5 scales, B.4.7 statistics) from the PDF, so its exact listener-count and instruction wording is unverified. The scale labels used here come from 3GPP reproductions.
- I could not find ITU-T P.808's own normative guidance on votes per stimulus. The figure of at least 60 votes per condition is a research recommendation (Naderi et al.).
- Not verified: whether the sideband WebSocket (wss://api.openai.com/v1/realtime?call_id=...) receives the WebRTC-only output_audio_buffer.started/stopped/cleared events in the unified-interface set-up. This needs a quick empirical check.
- No official or benchmark evidence exists on how well gpt-4o-mini-tts or the gpt-realtime-2.1 voices handle Gulf or Emirati dialect, or how the agent understands Emirati speech. A native-speaker pilot is needed.
- It is unknown whether gpt-realtime-2.1(-mini) reliably reads a script verbatim, which matters for generating fixtures after the 6 Jan 2027 TTS shutdown.
- gpt-live-1's language support (Arabic?) is undocumented, and it uses a different API (v1/live/sessions), so its suitability as a Gulf Arabic simulated caller is unknown.
- Needs testing in current Chrome with Playwright: whether overriding getUserMedia via addInitScript conflicts with --use-fake-device-for-media-stream (reported in a Puppeteer-era gist), and whether a remote WebRTC track fed to Web Audio still needs a muted, playing <audio> element.
- Node-side alternatives: @roamhq/wrtc is only confirmed on Node 20 and 22, not 24, and werift has no documented PCM-to-Opus input path. Both need a spike before relying on them.
- Exact audio-token rates per minute and the real per-call cost of gpt-realtime-2.1-mini are not verified, so the Phase 0 budget (about 360 RUN calls plus 400 CRAWL turns per configuration) needs a pricing check.
- Whether the OpenAI Evals API (file uploads with purpose='evals') is compatible with the planned ZDR configuration.
- I did not obtain Krippendorff's primary text on the 0.800 and 0.667 thresholds; the thresholds are cited from secondary sources.
