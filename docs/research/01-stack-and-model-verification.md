## 1. Next.js as the full stack (self-hosted)

### Verdict (researcher)

Recommendation: (b). Use Next.js 16.4.3 (then the Nov 3 security patch) for UI, admin, public APIs, the widget page and the loader script. Run one small separate Node worker process from the same repo and Docker image, as a second compose service, for the voice sessions and background jobs.

Why (b):
- Next.js gives no supported way to own long-lived server work:
  - no WebSocket API;
  - no public shutdown hook;
  - register() is documented only as a startup hook for observability.
- Module-level state can be duplicated across bundles. Next.js's own internals work around this with globalThis.
- Next.js's SIGTERM handler waits only for HTTP requests and after() callbacks, then calls process.exit(143). That cuts the sideband sockets.
- Your design needs no inbound WebSockets. The browser talks to OpenAI over WebRTC, and the sideband WebSocket is an outbound client. So the main benefit of a custom server (attaching a ws server) is irrelevant here.

**Shape of (b):**
- The worker is a plain TypeScript Node process (run with tsx, or built with esbuild) that shares a lib/ folder with Next.js. It owns:
  - POST /v1/realtime/calls (or receives call_id from Next.js);
  - the sideband WebSocket per call;
  - tool calls into Postgres, with RLS set per tenant on each transaction;
  - usage metering;
  - the job queue (for example pg-boss or Postgres SKIP LOCKED);
  - its own SIGTERM drain: stop accepting new calls, let active calls finish up to 10 minutes, then exit. Set stop_grace_period to about 11 minutes on the worker service only.
- Next.js talks to the worker through Postgres (rows plus LISTEN/NOTIFY) or a small internal HTTP endpoint behind the reverse proxy.
- Next.js can push live status to dashboards with SSE from a Route Handler. Turn off proxy buffering for those routes.

**Failure modes of (b):**
- Two processes to build, deploy, log and health-check.
- Shared code and env must stay in sync.
- An extra hop between Next.js and the worker adds a little latency and code.
- Restarting the worker still ends live calls unless you drain it. But deploying the UI no longer touches calls, which is the main win.

**Failure modes of (a), everything inside next start:**
- Works in production in practice, but nothing guarantees it.
- A plain module-level registry may exist as duplicate copies across route bundles and instrumentation, so you must use globalThis with Symbol.for.
- In next dev, editing a file re-creates the registry while old sockets stay open and are lost. Config changes and the memory limit restart the whole process.
- Every UI deploy SIGTERMs the process, and Next.js exits after HTTP drain, so active calls drop. Avoiding this needs NEXT_MANUAL_SIG_HANDLE (documented only in the Pages Router guide) plus your own signal handlers.
- Next.js's uncaughtException handler only logs, so session bugs leave a half-broken process running instead of a clean restart.
- Long SSE responses or after() work delay shutdown until SIGKILL.
- UI rendering load and audio-adjacent tool latency share one event loop.
- Acceptable only for a prototype, and only with globalThis plus manual signal handling.

**Failure modes of (c), a custom server hosting everything:**
- Officially discouraged.
- Cannot be combined with standalone output, so the Docker image needs full node_modules.
- server.ts is outside Next.js's bundler. You need a separate build, and its modules are different instances from those in Route Handlers, so sharing the registry still needs globalThis or IPC.
- Next.js auto-attaches its own upgrade listener, so you must route upgrades by path.
- WebSocket upgrade handling has recently had SSRF bugs.
- It keeps all of (a)'s problems: shared event loop, every deploy kills calls, uncaughtException only logs. Its one advantage is that you control shutdown fully, and a separate worker gives you that too without these costs.

**Widget:**
- Serve the embed page from Next.js and set per-tenant `Content-Security-Policy: frame-ancestors <tenant origins>` and `Permissions-Policy: microphone=(self)` from proxy.ts (Node runtime), or from a Route Handler that returns the HTML.
- Do not copy the docs' `microphone=()` example.
- Tenants embed `<iframe src=... allow="microphone">`.
- Serve a separately built loader from /public with explicit Cache-Control set through headers(), using versioned filenames. The default is max-age=0.

### Fact-check: the verdict holds

I checked all 26 claims against primary sources: the npm registry, GitHub releases, the v16.4.3 source on raw.githubusercontent.com, nextjs.org docs and blog, Vercel docs, Docker docs and MDN. 24 hold as stated. 2 need correcting, and neither changes the verdict.

1. **next dev reloading (claim 7) is out of date.** The 16.2 blog said Route Handlers still used the old reload system that clears `require.cache`. PR #91466, merged 2026-03-19, moved them onto Turbopack Server Fast Refresh. The 16.4.3 code (`participatesInServerHmr`) confirms this. A module-level session registry can still be re-created on edit, but less often, so the advice to keep it on `globalThis` still stands.
2. **The verdict's statement that option (a) needs NEXT_MANUAL_SIG_HANDLE to avoid dropping calls is overstated.** Next.js documents that it waits for pending `after()` callbacks before exiting. Wrapping each call's lifetime in `after()` would therefore delay shutdown, though only as a hack with no timeout control.

The other key facts are all confirmed:
- Version 16.4.3 is latest, needs Node >=20.9.0, and the November 3 security release is announced.
- The 'not a full backend replacement' text exists. There is no WebSocket upgrade API, and the upgrade handler behaves as described.
- Shutdown in `start-server.ts` works as described: `server.close()`, wait for `after()` callbacks, then `process.exit(143)`. NEXT_MANUAL_SIG_HANDLE is documented only in the Pages Router guide. `onServerClose` is protected.
- Next.js installs an `uncaughtException` handler that only logs. The finding misses that it does the same for unhandled rejections.
- `register()` is documented as an observability and startup hook.
- Custom servers are discouraged and cannot be combined with standalone output.
- The CVE-2026-44578 version ranges are right.
- The `after()`, Proxy, `headers()`, CSP, Permissions-Policy, `/public` caching and Docker grace-period facts are correct.

Verdict (b) holds and is if anything stronger: one Next.js app for UI, API and the widget, plus a small separate Node worker in the same repo and image for sideband sockets, tools, metering and jobs, with its own SIGTERM drain and a long `stop_grace_period`. Neither correction removes the main problems with (a) or (c): a UI deploy SIGTERMs live calls, process errors are only logged, one event loop is shared, and no official long-running-work API exists. One widget point to add: the Next.js CSP guide's examples use `frame-ancestors 'none'`, and browsers apply the strictest of multiple CSP headers. A global CSP in `next.config` would therefore block the embed route unless that route is excluded.

### Facts the fact-checker added

- Route Handlers now use Turbopack Server Fast Refresh in dev. PR #91466 was merged 2026-03-19 and is present in v16.4.3: participatesInServerHmr() covers all 'app' entries that are not edge. So the 'require.cache cleared for the import chain' description applies only to 16.2.x, webpack, or experimental.serverFastRefresh=false. Live sockets can still be orphaned when the registry module, or a module the update reaches, is re-run.
- Next.js also registers a process-wide unhandledRejection listener that only logs ('prevents them from crashing the process', process-error-handlers.ts in v16.4.3). Unhandled promise rejections in an in-process session manager therefore don't crash the process either. This strengthens the case for a separate worker with its own crash policy.
- In production, Next.js's shutdown calls server.close() without closeAllConnections() (that runs only in dev). Any long-lived HTTP response (SSE dashboards, long polls) blocks process exit until it ends or Docker sends SIGKILL.
- after() is a documented way to delay shutdown in next start: pending callbacks are awaited before exit. It could hold in-process calls open during a drain without NEXT_MANUAL_SIG_HANDLE, but it is a hack with no timeout or per-call control.
- The Next.js CSP guide's proxy and next.config examples both use frame-ancestors 'none'. In Proxy's execution order, next.config headers() run before Proxy. Browsers enforce every CSP header they receive, and 'Adding additional policies can only further restrict' (MDN, https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy). A global CSP with frame-ancestors 'none' in next.config therefore blocks the embed route even if Proxy adds a per-tenant policy, unless the global rule excludes that route. Whether Proxy's header replaces or adds to the config header was not verified.
- In v16.4.3 many custom-server methods (render, renderToHTML, renderError, render404, setAssetPrefix, logError, revalidate) log 'is deprecated in custom servers' warnings (next.ts warnDeprecatedCustomServerMethod). getRequestHandler, prepare and getUpgradeHandler are not deprecated. This supports the 'discouraged' framing for option (c).
- CVE-2026-44578 is rated High (CVSS 8.6), not just 'an SSRF'. Patched versions are 15.5.16 and 16.2.5, so 16.4.3 is not affected. The self-hosting guide also recommends a reverse proxy in front of next start.
- The only community answer on singletons (discussion #68572, unanswered officially) says 'now that everything runs in the same process, globalThis will work across different chunks'. No official Next.js doc confirms a single instance across route bundles.

### Open questions (resolve in Phase 0 or the named block)

- No official Next.js document guarantees that one server-only module imported by several Route Handlers is a single instance in Next.js 16.4.x Turbopack production builds. Only internal code (PR #95999) and community discussions say copies can exist.
- Is NEXT_MANUAL_SIG_HANDLE still officially supported for App Router apps? The 16.4.3 source still honours it, but it appears only in the Pages Router self-hosting guide, and there is no documented App Router place to register handlers (instrumentation.ts is an assumption).
- Does register() in instrumentation.ts re-run or behave differently during next dev reloads and restarts? The docs only say 'once when a new Next.js server instance is initiated'.
- The advisories for the November 3, 2026 security release (seven medium vulnerabilities) are not public yet, so the affected features are unknown.
- Not verified here (outside this topic): OpenAI Realtime sideband limits and behaviour, including session max duration, sideband reconnection to an existing call_id, and whether 'gpt-realtime-2.1-mini' exists and supports the unified /v1/realtime/calls flow.
- Not verified: whether request.signal reliably aborts on client disconnect for long SSE Route Handlers behind nginx in self-hosted next start.

## 2. gpt-realtime-2.1-mini and the Realtime sideband

### Verdict (researcher)

gpt-realtime-2.1-mini is a reasonable starting default on cost grounds, but only conditionally and not without testing. It is OpenAI's current mini Realtime model: released Jul 6, 2026, with no deprecation date, and the named replacement for gpt-realtime-mini, which shuts down Jan 20, 2027. It supports function calling, reasoning effort (assume a default of low), the 60-minute session maximum, EU data residency (+10%) and ZDR eligibility. Its tokens cost about one sixth (text) to one third (audio) of gpt-realtime-2.1.

The risks fall exactly on this use case:
1. OpenAI's own docs say mini is weaker at 'instruction following and function calling' and advise testing on the larger model first.
2. Community reports show 2.1-mini skipping tool calls because of stricter guardrails (fixed with prompt changes), non-English language drift and accent problems that include 2.1-mini, and echo self-interruption over WebRTC.
3. There is no Arabic evidence either way.
4. Realtime cannot be processed in the UAE region (US or EU only).

Recommended safeguards:
1. Keep the model ID configurable per tenant and fall back to gpt-realtime-2.1 for the hard cases. Before launch, run an Arabic (Gulf) and English eval set covering all 8 tools, including dates, times, phone numbers and names.
2. Make the server sideband the single owner of tool execution: it sends function_call_output and then response.create, deduplicates by call_id, and the browser ignores tool events.
3. Never let the model confirm a booking unless the response.done output actually contains a booking function_call that the DB then committed. Use confirm-before-write prompting, explicit 'call the tool when…' rules, reasoning effort low or medium, and language pinning in the instructions.
4. Create calls server-side with the standard API key through the unified interface (ephemeral-key calls had sideband 404s in Sep 2026).
5. Enforce the 10-minute cap with a server timer plus POST /v1/realtime/calls/{id}/hangup. A 200 only means teardown has started, so also close the browser peer connection from your own UI signal.
6. In the browser, use echoCancellation/noiseSuppression, consider gating the mic during assistant playback, and tune the VAD threshold.
7. For transcription, use gpt-transcribe or gpt-live-transcribe rather than whisper-1 or the gpt-4o-transcribe models, which are deprecated for Feb 26, 2027. Validate compatibility with WebRTC first.
8. Account for tier limits. Build tier allows 200k TPM and $500/month, which 50 concurrent calls are likely to exceed, so plan for Launch tier or above. Also compare GPT-Live 1 ($0.05/min, Build tier allows 50 concurrent sessions) as an alternative architecture.

### Fact-check: the verdict holds

The findings are accurate overall. I re-read every primary source myself. Model ID, release date, specs, prices, rate limits, tier caps, the 60-minute session limit, hangup semantics, transcription options and prices, deprecations, EU residency, ZDR, the UAE region limits and the 10% uplift are all confirmed. All community reports check out as secondary evidence. The corrections:

1. The server-controls page never uses the word 'legacy'. The sideband ownership quotes ('browser can still receive session events', 'execute the function once') sit under the GPT-Live subsection 'Assign one owner for each action'.
2. The 4096 max_output_tokens figure is not a conflict with the 32,000 model maximum. The default is `inf`, up to the model maximum.
3. The reasoning default of 'low' rests only on a non-staff forum post. OpenAI's migration guidance ('low instead of the default') suggests otherwise, so set the effort explicitly.
4. The cost ratio is overstated for long calls. Cached audio input on mini is 75% of the full model's price, and context is re-sent every turn.
5. Minor date and wording fixes in the ephemeral-key thread: it runs Sep 9 to 16, the fix is secondhand, and the split by key was intermittent.
6. The SIP guide's statement that the sideband 'behaves exactly like any other Realtime API connection' was missed. It partly answers the open question about sideband events.

The verdict still holds. gpt-realtime-2.1-mini is a reasonable, current, non-deprecated default on cost grounds for a bilingual booking agent, but only with safeguards:
- explicit reasoning.effort and language pinning
- a single server-side owner for tools, with booking confirmation grounded in tool and DB results
- an Arabic and English eval with a configurable fallback to gpt-realtime-2.1
- a server timer plus hangup
- browser echo controls
- a non-deprecated transcription model, tested on WebRTC
- Launch tier or above, with a concurrency load test

There is no official or community evidence on Arabic quality either way, and a live Realtime session cannot be processed in the UAE region.

## 3. OpenAI Agents SDK (TypeScript) for the server-side sideband

### Verdict (researcher)

Build the sideband with the Agents SDK, using the officially documented 'Browser audio with server-side controls' pattern. On the server, create new RealtimeSession(realtimeAgent, { transport: 'websocket', model: 'gpt-realtime-2.1-mini', tracingDisabled: true, outputGuardrails }) and call session.connect({ apiKey, callId }). The transport is OpenAIRealtimeWebSocket. Do not use OpenAIRealtimeSIP: it is SIP-only, throws on sendAudio, and validates SIP-specific turn-detection fields. Use examples/realtime-server-controlled as the template. It covers the multipart POST /v1/realtime/calls with the safety identifier, the strict rtc_ regex on the Location header, waiting for a session.updated that confirms instructions and tools, disconnect handling, hangup through openai.realtime.calls.hangup, and an expiry sweep. In that example the browser sends an audio-only SDP offer, never opens a data channel, and never sees the call ID.

Reasons:
(1) It is first-party and documented, with a maintained example merged in Aug 2026.
(2) Tools run on your server. RealtimeSession runs invokeFunctionTool and sends function_call_output plus response.create over the sideband for you. Tools get Zod schemas, timeouts and runContext.context, which is where you put trusted tenant and clinic IDs for row-level security.
(3) Approvals, transcript guardrails, history and usage aggregation come built in.
(4) You can still reach raw events through transport_event and session.transport.sendEvent, so you can drop to raw protocol for edge cases without leaving the SDK.
(5) The SDK already depends on ws and supports Node 22+.

Risks and mitigations:
(a) Pre-1.0 churn. Minor versions are allowed to break; there were 8 minor bumps from 0.13 to 0.21 between July and October 2026, and 0.21.0 changed usage typing. Pin the exact version (0.21.0), keep the SDK behind a thin internal adapter, and upgrade on purpose.
(b) The sideband over a WebRTC call relies on the generic callId option, and the SDK's own JSDoc still calls it SIP-only. The feature came from a docs PR with no SDK code change. Coverage of edge cases is thinner than for the browser path.
(c) interrupt() and guardrail cut-offs may do nothing on the sideband, because they depend on audio deltas the sideband may not receive (unverified). Plan to send response.cancel yourself when guardrail_tripped fires.
(d) Disconnect detection was a known gap (#684). Enforce the 10-minute cap with your own timer plus calls.hangup, and use transport 'disconnected' and an expiry sweep.
(e) The SDK emits no usage event. Read session.usage or listen to transport_event for response.done to meter per call. Persist raw usage details and narrow numeric types as 0.21 requires. Transcription usage may not be included.
(f) Tracing defaults to 'auto' and cannot be changed after connect. Set tracingDisabled: true or decide before connect, because these are patient conversations.
(g) gpt-realtime-2.1-mini is in the SDK's model type but is not the default (gpt-realtime-2.1). Set it in both the /v1/realtime/calls session config and the RealtimeSession model option.
(h) There is no official Next.js plus sideband example. openai-realtime-agents is stale (agents 0.0.5, legacy /v1/realtime/sessions ephemeral tokens, tools in the browser), and examples/realtime-next runs the session in the browser. Do not copy either for this architecture. In self-hosted Next.js, keep the per-call session registry in one long-lived Node process, or move the sideband into a small Node worker next to Next.js.

When raw ws is the better choice: if you only need tool calls, session.update context injection and response.done metering, the raw protocol is small. It means handling session.update, response.function_call_arguments.done, conversation.item.create (function_call_output), response.create and response.done, in roughly 200–400 lines. That gives full control and no dependency churn, but you give up schema validation, approvals, guardrails and history helpers. For a single developer I recommend the SDK pinned at 0.21.0, with raw ws as the fallback if items (b) to (d) cause trouble in testing.

### Fact-check: the verdict holds

Second, the release date of gpt-realtime-2.1 and 2.1-mini (Jul 6, 2026) is in OpenAI's official API changelog, so it is verified_primary, not secondary only. The WebSocket transport never sends output_audio_buffer.clear, which OpenAI documents as WebRTC/SIP-only and the SDK's own WebRTC transport always sends. The docs list only transcript deltas for WebRTC. DEFAULT_OPENAI_REALTIME_MODEL` ('gpt-realtime-2.1'), and _getMergedSessionConfig always adds `model: newConfig.model ?? this.#model` to session.update. For a call created with gpt-realtime-2.1-mini, the model must be set explicitly on RealtimeSession. It is undocumented whether the API rejects a model change or silently applies it. (https://raw.githubusercontent.com/openai/openai-agents-js/main/packages/agents-realtime/src/openaiRealtimeBase.ts)
- For WebRTC/SIP calls, OpenAI documents output_audio_buffer.clear, sent after response.cancel, as the way to cut off audio already being played. The SDK's OpenAIRealtimeWebSocket.interrupt() never sends it; only OpenAIRealtimeWebRTC.interrupt() does. A guardrail cut-off on a WebRTC sideband therefore probably needs session.transport.sendEvent({type:'response.cancel'}) plus {type:'output_audio_buffer.clear'}. Whether the sideband WebSocket accepts output_audio_buffer.clear is undocumented. (https://developers.openai.com/api/reference/resources/realtime/client-events, https://raw.githubusercontent.com/openai/openai-agents-js/main/packages/agents-realtime/src/openaiRealtimeWebRtc.ts)
- In the transport code, usage_update is emitted only from response.done. Input-audio transcription events trigger only a conversation.item.retrieve, and the 0.15.0 'duration usage' fix is about parsing events, not metering. So session.usage does not include transcription cost; billing needs the raw transcription.completed usage from transport_event.
- The official example's expiry sweep closes sessions after 30 minutes (closeExpired(30 * 60 * 1000), checked every 60 s). The 10-minute per-call cap therefore needs your own timer plus calls.hangup.
- The official example does not set tracingDisabled. Tracing defaults to 'auto' unless you disable it, which matters for patient conversations (data-residency and privacy review).
- PR #1762 shipped about 38 files of example code and tests (sdpPolicy.ts, sessionManager.ts, shutdown.ts, publicEventProjection.ts). Those are a ready template for SDP policy, idempotent cleanup and the browser event allowlist, beyond the docs alone.
- OpenAI's changelog (Nov 20, 2025) says DTMF events can be received over a Realtime sideband connection. The sideband is a first-class, maintained API feature on the platform side.
- tool() supports timeoutMs and timeoutBehavior (default error_as_result without outputSchema), so the verdict's 'tools get timeouts' holds. (https://raw.githubusercontent.com/openai/openai-agents-js/main/docs/src/content/docs/guides/tools.mdx)

## 4. Data and auth stack inside Next.js (Drizzle, Better Auth, pg-boss, next-intl, Turnstile)

### Verdict (researcher)

Yes. The combination works in one self-hosted Next.js 16 (App Router, Node runtime only) app on PostgreSQL 18. Use Drizzle on node-postgres, Better Auth with the organization, twoFactor and nextCookies plugins through the Drizzle adapter, next-intl, and Turnstile siteverify in Route Handlers. I recommend one extra worker process built from the same codebase and Docker image, with a different entrypoint (e.g. `node dist/worker.js`), for pg-boss workers and other long-lived work. pg-boss could run inside the Next.js process via instrumentation register() behind a NEXT_RUNTIME==='nodejs' check, and nothing in the docs forbids it. But neither Next.js nor pg-boss documents that pattern, and a separate process gives cleaner shutdown via boss.stop(), no duplicate workers from dev reloads, and keeps job load off request latency. (Inference, not researched here: the long-lived sideband WebSockets, about 50 at 10 minutes each, also fit better in a long-lived worker than in Route Handlers.)

Gotchas to design for:

1. **RLS with pooling.**
   - Never use session-level SET. Wrap every tenant-scoped request in db.transaction(tx => { tx.execute(sql`select set_config('app.tenant_id', ${tenantId}, true)`); ... }). Drizzle's node-postgres transaction pins one pooled client, and is_local=true resets at COMMIT/ROLLBACK, so nothing leaks between requests.
   - Policies should use current_setting('app.tenant_id', true) so that a missing tenant means default-deny.
   - Run the app as a non-owner role without BYPASSRLS, or add FORCE ROW LEVEL SECURITY. Run migrations as a separate owner role.
   - Every tenant query must go through the wrapper. A query on the plain `db` outside it sees no tenant.
   - Holding a transaction per request uses up the pool (default max 10), so size it.
2. **Better Auth vs RLS (inference, not documented).** Better Auth runs its own queries outside your tenant transaction. Keep its tables (user, session, account, verification, organization, member, invitation, twoFactor) out of tenant RLS, or give them their own policies. Use session.activeOrganizationId (or the member lookup) as the source of app.tenant_id.
3. **Drizzle versions.**
   - The docs site now shows v1 APIs (pgTable.withRLS, defineRelations), but npm latest is 0.45.4, which uses .enableRLS(). Pin one line deliberately. If you go to v1 RC, use Better Auth's relations-v2 entrypoint.
   - There are no native tstzrange columns: use customType.
   - There is no EXCLUDE constraint support: put btree_gist and EXCLUDE USING gist in a `drizzle-kit generate --custom` SQL migration, and catch SQLSTATE 23P01 in booking code.
4. **Better Auth security settings.**
   - Use >= 1.7.7 (1.7.14 is current).
   - Set organization({ requireEmailVerificationOnInvitation: true }), because GHSA-fmh4-wcc4-5jm3 lists >= 1.6.14 as affected with no patch.
   - Avoid magic-link together with DB-stored OAuth state on older versions.
   - If you use cookieCache with 2FA, stay above 1.4.6.
   - Set ipv6Subnet for the rate limiter.
   - Gate pages and Server Actions with auth.api.getSession, not only proxy.ts.
5. **Runtime.** Avoid the Edge runtime everywhere: pg TCP sockets and Better Auth DB calls need Node. Next 16 proxy.ts defaults to Node and cannot be switched. pg is auto-externalized.
6. **pg-boss.**
   - Needs Node >= 22.12, so use a node:22/24 base image, and PG 13+.
   - It creates its own schema on start(), so the role needs schema rights or you set migrate:false and migrate separately.
   - Its pool (default 10) adds to the app's pool; count connections against max_connections, or pass `db` to reuse one pool.
   - Use fromDrizzle(tx, sql) to enqueue a job atomically with a booking.
   - useListenNotify is incompatible with PgBouncer transaction mode.
7. **i18n.** next-intl 4.14.x supports Next 16 (proxy.ts, root params on 16.3+). Set <html lang dir> yourself, from new Intl.Locale(locale).getTextInfo().direction or a simple {ar:'rtl'} map, and use CSS logical properties.
8. **Turnstile.** Call siteverify from a Node Route Handler with fetch and a timeout. Tokens are single-use and expire after 300s. Check hostname and action. Take remoteip from your reverse proxy's headers because NextRequest.ip no longer exists. Better Auth's captcha plugin can cover the auth endpoints.
